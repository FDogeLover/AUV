## 编码规范（关键约束！）

### 飞控固件 .c/.h 文件

**编码是混合的**——不能一概而论：

| 编码 | 典型文件 | 说明 |
|------|---------|------|
| **GBK** | `Ano_Scheduler.c`, `Ano_Math.c`, `Drv_*.c` | 大多数原始固件文件，含中文注释 |
| **UTF-8** | `my_protocol.c`, `my_protocol.h` | 稳定性重构时改写，中文在 UTF-8 下正常 |

**编辑规则（严格执行）：**

```
1. 禁止使用 Read/Edit 工具操作 .c/.h 文件！
   → 可能静默转换编码，导致中文注释永久损坏

2. 必须使用 edit_firmware.py 脚本编辑：
   python edit_firmware.py show <file>       # 查看编码
   python edit_firmware.py replace <f> <o> <n>  # 安全替换
   python edit_firmware.py verify <file>     # 验证编码

3. edit_firmware.py 自动完成：检测编码 → 原编码读取
   → 替换 → 原编码写回 → 验证编码不变

4. 每次编辑后必须 run verify 确认编码完整
```

## 关键设计决策

### 下行帧协议（飞控 → Pi，`my_protocol.c` `pi_send()`）— 2026-07-04 已重构并真机验证通过
- 拆成两种帧，格式统一为 `AA | frame_id | len | DATA | checksum | 0xFF`：
  - **帧1（0x01，飞行关键帧，24字节数据）**：`Loop_50Hz` 调用，`mission_stage`/`roll,pitch,yaw`/`fusion_state`/`unlock_sta`(真实解锁状态)/`x_int,y_int`(光流积分)/`laser_height_cm`/`of1_dx,dy`(光流融合速度)/`of_quality,link_sta,work_sta`
  - **帧2（0x02，调试扩展帧，18字节数据）**：`Loop_2Hz` 触发但内部降频到约2.5秒一次，`fc_vel_xyz`(凌霄IMU速度估计)/`of_acc_xyz,of_gyr_xyz`(光流模块自带IMU原始数据)
  - 两帧共用 USART2，`pi_send()` 统一驱动发送（`Send_str_by_len` 整帧阻塞发送，不再逐字节跨tick分段），避免了帧交织 bug，帧1实际到达率约 50Hz（之前分段发送方式只有 ~1.7Hz）
- Python 侧 `Lprotocol.py` `listen_fc()` 按 `frame_id` 分发解析，`Serial_fc` 串口超时从 0.05s 改成 1.0s（帧变长后需要更长超时才能收全）
- `re_fc`/`rxbuffer` 现在是 14 个字段（見 `main.py` 里 `re_fc` 注释的字段顺序）

### 上行帧（Pi → 飞控）
- `AA 01`：T265 速度帧（vx,vy,yaw），100Hz，整帧一次性 `ser.write()`，不受分段发送问题影响
- `AA 02`：指令帧（task_sta/com_x/y/z/yaw），50Hz
- `AA 03`：T265 位置帧（x,y,z，cm，s32，小端序），新增。**飞控侧 `my_protocol.c` 会解析存入 `t265_pos_x/y/z`，但目前没有任何代码消费这个数据**——原计划通过 CMD 0x32（通用位置型传感器数据）转发给凌霄IMU，已确认凌霄IMU固件不支持该通道，转发部分已回退，只保留飞控本地接收

### 飞控 ↔ 凌霄IMU（USART5，500000波特率，匿名通信协议V7，与 Pi↔飞控完全独立的第二套协议）
- 飞控本身**没有物理IMU**，姿态自稳完全由外部"凌霄IMU"模块自己完成（自己的加速度计/陀螺仪 → 姿态融合 → PID → 电机混控 → CMD 0x20 PWM 值发回飞控 → `ESC_Output()` 直接转发给电调），跟 Pi/T265 无关
- **定点悬停**（不漂移）依赖外部速度参考：`ext_sens.gen_vel`（CMD 0x33）默认用 T265 速度（`pi_ctrl_mode` 开机即强制=1，见 `User_Task.c:26`），T265完全失效时才会退回光流。纯IMU（无T265无光流）无法定点，会漂移
- "倾角保护"来自 `Mycode/angle_protect.c` 的 `Attitude_Check()`：roll/pitch 超过 30° 触发失控保护，跟凌霄IMU的融合算法无关，是这块板子自己加的安全阀
- `flex_send_t265_vel()`/`flex_send_guangliu_vel()`（`my_protocol.c`，走 0xF1/0xF2 灵活格式帧）只是调试可视化通道，转发 T265/光流速度给凌霄IMU官方上位机画波形，**不影响实际导航融合**
- **凌霄IMU官方上位机**：`D:\Competition\自组无人坤\1\匿名上位机.exe`（"匿名科创"品牌，V7.3-20240423）。**连接方式是 USB HID（需要专用"匿名控制台"设备，也支持UDP/TCP），不经过现有的 Pi↔飞控串口链路，只能有线连接，无法在无缆自由飞行时实时监控**——定位是地面台架调试工具（比如拆桨接USB测起飞时序），不是飞行中监控手段。
  - 功能模块：**飞控状态**(实时飞行模式/锁定/姿态/高度/GPS/电压)、**数据显示**(完整协议帧浏览器，Frame ID 0x01~0x51逐字段展开)、**飞控参数**(166项参数表)、**功能触发**(磁力计/陀螺仪/水平/6面校准+清空APP进固件升级模式)、**凌霄IMU**(控制参数微调+校准+遥测频率配置)、**地图显示**(需GPS)、**连接设置**(USB HID/UDP/TCP)
  - **关键参数**：`TAKEOFFHIGH`（起飞后自动尝试定高的目标高度，cm）/`TAKEOFFSPEED`（起飞爬升速度，cm/s）——确认 `OneKey_Takeoff()` 触发的是IMU自己独立的"按固定速度爬升到固定高度后自动定高"逻辑，用这两个参数，不是飞控算出来的
  - **关键遥测字段**（Frame 0x06 展开）：`FC_STA_FlyMode`（0=姿态自稳/1=自稳+定高/2=定点飞行/3=程控飞行）、`FC_STA_SFlag`（0锁定/1解锁）、`FC_STA_CID/CMD0/CMD1`（当前执行功能，对应0xE0帧）；（Frame 0x0E 展开）`FC_STA_I_GVEL`/`FC_STA_I_AALT`（外接速度/测高传感器连接状态，即T265/光流是否被IMU认为在线有效）——如果以后做**台架通电测试**（拆桨、USB直连飞控），可以实时看 `FC_STA_FlyMode` 在一键起飞前后有没有真正切换，验证已知问题6的候选③

### 飞控闭环控制
- `height_set()`（Kp=0.8, Ki=0.05, Kd=0.2，输出限幅±30）**不是位置式PID输出目标高度，而是算出一个垂直速度指令**：`User_Task.c:169` 在 `mission_step==5`（视觉控制阶段）调用 `tar_setdata(com_x, com_y, height_set(ano_of.of_alt_cm, com_z), com_yaw)`，`tar_setdata()`（`my_fun.c`）把这个输出塞进 `rt_tar.st_data.vel_z`（注释标注"垂直速度 cm/s"），通过匿名协议V7的 `0x41` 帧发给凌霄IMU——高度控制实际是**飞控外层算速度指令 + 凌霄IMU内层执行**的级联结构，不是飞控自己直接闭环到位置
- 上位机控制周期 30ms，速度帧 100Hz，指令帧 50Hz
- `Mission_GPT.py`：T265 连接成功后会等追踪置信度达标（默认8秒超时）才允许进入定点/起飞，否则跟T265完全失败一样需要人工输入 `YES` 确认
- `DRONE_DRY_RUN=1` 环境变量：桌面测试用，`se_fc[2]`(task_sta) 永远为0，飞控不会解锁

## 已知未解决问题（供下次会话参考）

1. **T265 冷启动检测失败**：板子重启后 T265 经常检测不到，必须物理拔插一次才能恢复。已实测确认 `uhubctl` 软件断电重连**不可靠**（对已连接设备的验证成功过一次，但对冷启动失败场景连续两次尝试都没能恢复），根因怀疑是 USB3 链路训练卡在 `Rx.Detect` 状态，需要真正的物理断开信号，软件模拟不出来。目前无解，只能靠人工记得拔插
2. **光流模块坐标系可能跟机体不对齐 — 已关闭：2026-07-06 六次独立测试(4次X轴+2次Y轴)全部确认坐标对齐，此前结论是问题6节流bug的假象**：最早用手持晃动测试对比 T265 速度 vs 光流 `of1_dx/dy`，同轴相关性弱、交叉轴相关性更强，暗示可能差了约90°旋转，但当时样本量小(~4秒晃动)且节流bug(问题6)还没修，下行数据有秒级滞后，`analyze_of_t265_correlation.py` 的±5采样点(±250ms@20Hz)时延扫描根本补偿不了这么大错位。2026-07-06 节流bug修复后，先用1.0m单程X轴平移复测(302样本)，同轴相关性峰值0.60 > 交叉轴0.15，初步不支持90°旋转假设；当天晚些时候(commit `d11c354`，板载 `basic/test_data_20260706/`)又追加了4轮独立测试(`x_translate_single`/`x_translate_retest`/`x_translate_1p8m`(1.8m单程)/`x_translate_aligned`)以及2轮Y轴平移测试(`y_translate`/`y_translate2`)，用 `analyze_of_t265_correlation.py` 逐一复核：

   | 测试 | 同轴相关性峰值 | 交叉轴相关性峰值 |
   |---|---|---|
   | x_translate_single | 0.75 | 0.38 |
   | x_translate_retest | 0.76 | 0.37 |
   | x_translate_1p8m | 0.83 | 0.60 |
   | x_translate_aligned | 0.78 | 0.37 |
   | y_translate | 0.51 | 0.18 |
   | y_translate2 | 0.50 | 0.13 |

   六次测试同轴相关性全部明显高于交叉轴，X/Y轴各自独立验证，**结论：光流坐标系与机体对齐，此前"90°旋转"怀疑确认是节流bug造成的数据滞后假象，此问题关闭**，不需要再重复X/Y平移测试来验证坐标对齐本身。（后续如果又出现同轴/交叉轴相关性异常，再重新怀疑物理安装问题；这些原始数据只存在于 ubuntu-pi 的 `basic/test_data_20260706/`，本机仓库没有同步一份，需要时用 `scp` 拉取。）
3. **T265 与光流数据融合 — 2026-07-06 决策：暂不做，优先级降低**：问题2(坐标对齐)已基本排除，前提条件不再阻塞。但翻查当天所有测试的 `T265_CONFIDENCE`/`of_quality` 记录，**T265追踪置信度全天保持满值3，光流质量全天保持240~255高位，没有一次出现过"T265质量下降但未完全失效"的中间状态**——而这正是融合算法相对于现有二元切换（T265正常用T265、彻底失效才切光流）真正能带来增量价值的场景。当天实际遇到的问题（节流延迟bug、起飞高度污染、一键降落丢失、激光阈值bug、XY漂移）都不是传感器质量下降造成的，融合解决不了这些。**结论：没有实测证据支撑做融合的必要性，优先级排在后面**，等以后真的观测到T265置信度下降/光流质量下降的场景，再重新评估。
4. **凌霄IMU 原始加速度计/陀螺仪（CMD 0x01）**：协议里定义了，但 `ANO_DT_LX.c` 里这部分解析代码从一开始就被注释掉，从未启用。如果以后想拿凌霄IMU自己的原始IMU数据做振动分析，需要先启用这部分
5. **Keil 编译警告**：这次协议重构编译时报过警告（具体内容未记录），未来遇到问题可以先查一下这些警告有没有关联
6. **高度控制异常 — 根因已定位并修复（通信层节流bug），修复效果待真实飞行验证**：2026-07-05 真机测试最早发现高度 setpoint 大幅变化时（比如0.5m/1.5m阶跃）实际高度几乎不跟随、且 setpoint 不变时也会缓慢自主"爬升"。排查过程中依次排除了倾角补偿假设（多次测试倾角全程<3.5°，数学上不够解释误差量级）、怀疑过光流模块激光传感器本身有固定偏差或响应滤波滞后（现场目测实际高度比日志高约0.3m，且用 `laser_height_monitor.py` 实测"抬起放下"确认了3-10秒的滞后）。

   **根因（已定位并修复）**：`Lcode/Lprotocol.py` 的 `listen_fc()` 里 `time.sleep(0.05)` 缩进对齐到 `while` 循环体，导致不管有没有解析到完整帧、每轮循环都强制睡50ms，把下行数据读取吞吐量限制在约20帧/秒，远低于飞控实际50Hz发送速率，造成下行数据（含激光高度、roll/pitch、光流速度等所有帧1字段）持续积压在串口接收缓冲区，`listen_fc()` 读到的其实是几秒前的旧数据——这不是传感器问题，是纯软件bug。**已修复**：sleep 改为只在真正空闲（`self.ser.read()` 超时无数据）时触发；`listen_start()` 加了 `reset_input_buffer()` 清理启动前残留的陈旧字节；发送/接收线程都加了 `serial.SerialException` 捕获+日志报警（原来串口异常会静默杀死线程，无任何提示）。**修复已用手持"抬起放下"测试验证滞后消失**。

   **这个bug大概率是高度异常和光流坐标对齐（问题2）相关性一直偏弱的共同根源**——光流速度和激光高度都走这条链路，如果存在秒级滞后，`analyze_of_t265_correlation.py` 的±5采样点(±250ms@20Hz)时延扫描根本补偿不了这么大的错位。

   **2026-07-06 真机验证：节流bug修复有效，高度阶跃测试通过**。同时发现并修复了另外两个独立问题，一并记录：

   - **状态机没有"到达后停留观察"机制**：原逻辑是 `dz < posthreshold_z`(20cm) 一满足就立刻切下一个航点，导致阶跃测试中高度从未真正稳定就已经在往下一个目标走。已在 `Mission_GPT.py`（`basic/` 和全功能版都改）加了 `arrival_hold_s=3.0` 强制停留时间，`arrival_timeout_max` 相应从 5.0s 加到 `5.0+arrival_hold_s`。修复后实测：1.5m/0.5m 阶跃都能精确稳定在目标±1cm（此前从未真正到达过目标就被切走）。
   - **起飞目标高度被硬编码默认值污染（已修复）**：`main.py` 里 `se_fc` 初始数组 `se_fc[5]`(com_z字段) 默认硬编码为 `120`(cm)，而 `Mission_GPT.py` 的 `takeoff()` 函数触发 `se_fc[2]=1`(task_sta，让固件执行一键起飞) 时，从未把 `se_fc[5]` 更新成本次航点真正的目标高度——飞控固件 `User_Task.c:155-156` 的一键起飞逻辑是直接用 `received_data.com_z` 当目标高度传给凌霄IMU(`OneKey_Takeoff(received_data.com_z)`)，于是不管 router.txt 设的是多少，实际起飞目标一直是残留的默认值120cm。2026-07-06首次测试时目标0.5m，起飞却冲到1.20m、15秒都没能收敛，验证了这个假设。**已修复**：`takeoff()` 里改成先把 `se_fc[5] = int(target_h_cm)` 写入、再触发 `se_fc[2]=1`。修复后重测起飞精确落在0.52m，问题消失。

   **仍待验证**：重新做一次X轴平移测试，重新跑 `analyze_of_t265_correlation.py` 看光流坐标对齐（问题2）相关性是否显著提升。

    ```python
    if laser_height_cm > 50:   # 只有原始值>50(cm)时才更新_last_laser_height_cm
    ```

12. **`land()` 触发降落缺少速度门槛，降落成功率与触发时机(是否真正静止)强相关 — 根因已定位并修复，2026-07-07 真机验证有效**：commit `d11c354` 记录"验证降落成功与触发时机(是否真正静止)强相关"。翻查 `land_confirm_test2`/`verify_fixes_test` 两份归档数据，触发降落前最后几帧 `vx`/`vy` 显示还有约 -1~-3 cm/s 的残余速度，并非真正静止；2026-07-07 T265矫正验证飞行(第二次，微调后)里这个残余速度更大，到过-0.03~-0.12 m/s，同一次飞行还出现了"降落确认超时"和目视可见的起降抖动。当前 `land()`/`navigate()` 的到达判定原本只看位置误差(`dz`/`xy_thresh`)和停留时长(`arrival_hold_s`)，**没有检查速度是否已收敛到接近0**。

13. **N10P雷达细杆子(绕障目标)测距不稳定，命中角度和距离读数都会跳动 — 2026-07-07 台架测试确认，角度基准和平板测距精度已验证通过**：这是为"水平面杆子绕行"新增雷达功能（`drone_control/basic_radar/`）之后的台架测试结论。

    **已验证通过的部分**：
    - 角度基准：现场核对当前物理安装位置，0°对应机体+X方向，90°对应机体-Y方向，已写入 `Lcode/Lradar.py` 的 `radar_angle_to_body_xy()`（换安装位置需要重新核对，函数注释里已标注）。
    - 平板测距精度：0.5m处测得504~515mm(误差4~15mm)，0.7m处测得700~702mm(误差0~2mm)，均在手册标称±3cm精度内。

    **细杆子(模拟绕障目标)测距不稳定**：同一根杆子摆在大致同一方位(-180°附近)，分别测了65cm/30cm/45cm三个距离：
    - 65cm：命中170°/171°/178°三个角度，读数667~758mm，与真值误差17~108mm
    - 30cm：只有170°/171°命中，读数726~741mm，**完全没跟踪到杆子从65cm移到30cm这个变化**（应该测出~300mm，实际还是7~74cm量级）
    - 45cm：命中角度换成完全不同的179°，读数478mm，误差只有28mm（这次反而准）
    - 移走杆子后确认170°/171°方向的真实背景在7.2m外——证明前面几次的近距离读数确实是杆子的真实回波，不是背景噪声也不是数据阻塞/跨进程缓存导致的幻影（已排查：每次台架测试都是全新SSH进程+全新串口连接，460800bps下内核缓冲区只能保留几十毫秒数据，不可能跨进程保留分钟级旧值）。

    **结论**：命中角度每次都会跳动，测距准确性在"还算准(±3cm级)"和"完全跟丢(偏差达数十厘米)"之间摇摆，不是一个可以标定补偿的固定偏差，很可能是TOF雷达对细长目标常见的"混合像素/边缘效应"——扫描线打中杆子中心时测距较准，擦边命中时距离被杆子和背景的混合回波拉偏。**对绕障算法的影响**：不能假设雷达能持续、准确地追踪细杆子的距离，需要多帧统计（比如滑动窗口内取中位数而非单帧最近值）并接受"部分时刻完全测不到"的现实；更保守的做法是把"检测到回波"当二元触发信号而不完全信任距离数值本身。

    **动态响应测试**：物体在雷达前移动/晃动时，每0.4秒轮询一次 `get_nearest()`，约一半采样时刻拿到的是更近的移动目标，另一半会退化成报告更远的固定背景——说明瞬时轮询同样会漏检移动目标，跟静止目标的漏检是同一类问题，不是移动特有的。

    **命中率随距离变化 — 2026-07-07 补充测试，规律非常清晰**：静止细杆子固定不动、连续10次独立采样(1秒/次)得到的命中率基线：50cm处4/10(40%)，30cm处7/10(70%)——证明"离近=命中率高"。之后换成实际避障用的粗杆子重新测（注意：粗杆子这几个距离点跟前面细杆子的65/30/45cm不是同一根杆子，不能直接横向比较误差大小，但命中率的距离依赖趋势是一致的）：

    | 距离 | 命中率 | 命中时读数误差 |
    |---|---|---|
    | 70cm | 90%(9/10) | -10~+22mm |
    | 1m | 70%(7/10) | -47~+10mm |
    | 1.55m | 10%(1/10) | -21mm |

    **结论：70cm→1m命中率下降平缓，1m→1.55m断崖式下跌，这款雷达对杆状目标的可靠有效探测距离上限大概在1m左右**，超过这个距离命中率会显著恶化。这个数字直接决定绕障算法能规划出多少反应时间/安全距离，是目前最重要的一条工程结论。

    **调参数提高命中率 — 已查证，没有找到确认可行的软件调节手段**：查阅了《N10 Plus通讯协议》和ROS驱动源码(`lslidar_driver.cc`)，协议文档只记录了电机启停两条指令，没有"设置转速"的串口命令格式；ROS驱动里出现的`min_range`/`max_range`/`compensation`等参数都是驱动层软件过滤，不影响物理层命中率；产品参数表虽然写着"扫描频率6~12Hz"暗示转速可调、"支持双回波"暗示能拿到边缘目标的两个回波，但协议文档和驱动源码里都没找到怎么设置/读取这两项，需要联系镭神智能技术支持要完整参数协议才能确认。**目前唯一确认有效的提升手段是物理层面：让目标更近**，不是调雷达参数。

    **参考镭神官方 N10P + slam_toolbox ROS2 建图包(`D:\Competition\自组无人坤\雷达\leishen_n10p_ws`)得到的启示**：
    - 官方 `obstacle_detector.py` 用的是"角度维度空间聚类"（相邻点机体坐标系距离<eps=0.15m即同一聚类，聚类点数<min_samples=3整体丢弃孤立噪声点）来识别障碍物，不是我们最初设想的纯时间序列思路。
    - `slam_fix_node.py` 里的注释确认"N10P驱动bug：数组大小波动±1"是官方也承认的硬件/协议固有问题，佐证我们自己遇到的丢点、幽灵点不是 `Lradar.py` 实现的bug。
    - **移植空间聚类到 `Lradar.py` 后用真实数据验证**：`Serial_radar.get_obstacles()`(新增)能干净地把房间背景墙/家具聚类出来，孤立噪声点被正确过滤——但**细杆子在单帧里通常只产生1个孤立点，天生凑不够min_samples≥2的门槛，会被和噪声一起误杀**，说明空间聚类只解决了"大障碍物 vs 噪声"，解决不了"细杆子 vs 噪声"（两者在单帧空间特征上几乎无法区分，都是孤立单点）。

    **`PoleTracker`（`Lcode/Lradar.py` 新增） — 空间聚类+多帧时间持续性组合，已用真实杆子验证有效**：思路是聚类负责一帧内识别大障碍物(排除)，剩下的孤立/小聚类候选点交给滑动窗口做时间维度确认——噪声不会重复出现在同一角度附近，杆子会（哪怕命中率不到100%）。真实测试(1m处杆子，10次1秒轮询，`min_hits=3, window=6`)：8次候选里有8次在359-360°附近重复出现(953-980mm)，其余5个各只出现1次的噪声候选(253°/204°/251°/202°/243°)全部被正确排除，未确认判定 `angle_deg=359.6°, distance_mm=969.0(误差-31mm), hits=5`。**用户明确的实际约束**：只需要1m以内的探测范围（够用，命中率70-90%区间），实际运行时无人机会沿路径主动搜寻杆子而不是指望远距离静态探测，后续计划加视觉辅助定位——`PoleTracker` 目前定位是给雷达侧提供候选确认信号，配合视觉一起用，不是唯一的探测手段。

    **待实测验证的飞行动态干扰（2026-07-07 提出，尚未测试，等真正装机/试飞时再讨论）**：目前所有测试都在完全静止的台架上做的，没有验证过两类飞行特有的干扰：
    - **振动**：电机/桨叶转动会晃动雷达本体，现有的命中率/误差数据(70cm~90%、1m~70%等)都是零振动环境下测的，实际可能更差。建议装机测试前先做"拆桨接电、只让电机转、雷达固定在机身上"这种台架振动测试，不需要真正起飞。
    - **yaw旋转对`PoleTracker`的影响 — 已用几何关系想清楚，是否要处理取决于飞行场景**：`PoleTracker`的时间持续性匹配假设两次轮询之间机体朝向基本不变(角度容差`angle_tol_deg=4°`)，如果飞机在轮询间隔内有yaw旋转，杆子在机体系里的角度会跟着偏移同样的量——这是确定性的几何效应，不是随机干扰，只有当"yaw角速度 > 容差/轮询间隔"时才会打破持续性匹配（例如1秒轮询、4°容差对应约4°/s的yaw角速度上限）。**用户判断**：绕障搜寻阶段飞机是直线巡航、朝向基本不变，这个问题在当前场景下不成立，暂不处理；如果以后加"原地转圈主动扫描找杆子"这类大角度yaw行为，或者轮询频率提高（间隔缩短会让同样yaw角速度更容易破坏匹配），需要回来加"用yaw变化量补偿历史候选点角度"的机制。

    **2026-07-07 真实飞行验证：`PoleTracker`未能复现台架效果，根因是"接近目标时的几何方位角摆动"，不是yaw漂移** — 首次在真实飞行(而非静止台架)中测试，杆子摆在起飞点180°方向1m处，router.txt改成安全距离(`-0.6,0,1.0`，离杆子留0.4m余量)后飞行，同步跑`PoleTracker`轮询(0.5s一次)。结果：飞行全程35秒里，"180°"这个角度桶确认的距离稳定在1440-1456mm，几乎不随飞机接近而变化——但飞机确实从起飞点飞到了X=-0.6m附近，如果这真是1m处的杆子，测到的距离应该从~1m逐渐缩短到~0.4m。**结论：这个"180°确认"抓到的其实是背景墙特征，不是杆子**，真正的杆子信号被同一时间大量单次出现的候选噪声(6°/14°/350°/358°等)淹没，没能在某个稳定角度反复攒够`min_hits`。

    排查发现：**yaw漂移很小(全程1.89°~4.97°，摆动3.08°，本身在4°容差内)，不是主因**。用实际飞行轨迹反算杆子相对机体的真实方位角：起飞点(≈180°) → 飞到X=-0.57/Y=0.065时方位角变成≈161°，**摆动了约19°**，远超4°容差。根因是飞机接近目标的同时Y方向有约6.5cm偏移（跟问题11的Y漂移是同一现象），只要目标不严格在飞行路径正前方延长线上，飞机越靠近，视线方位角摆动越剧烈，是纯几何效应，跟传感器/算法实现无关。

    **方法论层面的结论**：`PoleTracker`当前"固定角度容差"的设计只适用于飞机相对目标基本静止或远距离慢速接近的场景，一旦飞机主动接近一个不在正前方的目标，方位角变化速度会远超固定容差能覆盖的范围——**不是简单调大`angle_tol_deg`能解决的**（调大到能覆盖19°摆动会严重牺牲抗噪声能力）。真正的修复方向需要用飞机自身位置变化量，实时重新推算"如果这是固定目标，它现在该在哪个角度"，而不是拿固定容差比对历史角度——这已经超出调参范围，需要专门设计，目前尚未动手，留待后续。

    **2026-07-08 已按上述方向重构并接入导航流程，回放验证有效，但`yaw_sign`仍未标定**：`PoleTracker`匹配逻辑改成世界系位置聚类——`update(radar, x_m, y_m, yaw_rad)`把每次轮询的候选点用`Lradar.py`新增的`body_to_world_xy()`(和逆变换`world_to_body_angle_dist()`)转换到世界系坐标再存历史，`confirmed_poles()`按世界系欧氏距离(`world_eps_m`，取代了`angle_tol_deg`/`dist_tol_mm`)分组，返回`{'x','y','hits'}`(世界系坐标，不再是机体系角度/距离)。**验证方式**：07-07真机测试当时雷达点云没有记录进飞行日志(雷达轮询是独立进程)，只能用真实T265轨迹(`pos`/`yaw`)+按台架实测命中率合成的雷达候选点回放对比新旧算法(`drone_control/tools/replay_pole_tracker.py`)。**踩过一个坑**：第一次直接用飞行日志原始记录(~65ms间隔)喂给两版算法，因为`window=6`是"6次轮询"不是"6条日志记录"，不按真实0.5秒轮询间隔重采样的话方位角根本来不及摆动，新旧版都在悬停阶段秒确认，测不出问题——修复后（`resample_trajectory()`按0.5s重采样）5个随机种子测试显示：新版一旦确认就全程保持(0次dropout)，旧版在接近/摆动阶段反复丢失确认(最差种子连续9帧丢失)。**已接入`Mission_GPT.py`的`navigate()`**（仅`basic_radar/`版本）：`DRONE_RADAR_ENABLED=1`才启用(默认关闭)，检测到确认的杆子距当前位置<`POLE_DANGER_DIST_M`(0.6m)就悬停，不做绕行；悬停后真实障碍物会持续被确认、不会自动恢复(刻意保守，需要人工遥控接管)，只有误报才会自动恢复导航。**`yaw_sign`（世界系旋转方向）依然没有真机标定**——回放验证用的是同一个假设值(`yaw_sign=1`)生成合成数据和跑算法，天然自洽，不能证明这个符号对不对，这次接入导航后这个值直接决定悬停判断用的世界坐标准不准，**下次真机操作时应该优先做这个标定**（参照`debug_coordinate.py`当年标定T265坐标系的方法：固定已知方位目标、转动机体、看哪个符号让算出来的世界坐标基本不动）。

    **2026-07-08 台架手持转动标定尝试失败，改为留到真机飞行时标定**：新增了`calibrate_yaw_sign.py`（雷达+T265刚性固定，实时对比`sign=+1`/`sign=-1`算出来的世界坐标），台架手持转动测试两轮：转到约90°时`sign=-1`更接近不变(漂移0.79m vs `sign=+1`的1.51m)，但再转到约135°时结果反过来了(`sign=+1`漂移1.54m 反而比`sign=-1`的1.62m略小)——两轮结果矛盾，判断不出稳定的符号规律。怀疑根因是手持转动的转轴不经过雷达/T265光心，转动本身会引入一个"假的"平移分量，跟符号误差的效应混在一起分不开，加上细杆子本身命中角度就有几度抖动(问题13已知的"混合像素"效应)，在大转动角度下被放大。**结论：台架手持转动这种标定方式不够干净，不可靠，已放弃**，决定留到真机飞行时用无人机自身的yaw转动做标定（比手转更精确、没有转轴偏移问题）。另外这次测试顺带发现雷达实际串口是`/dev/ttyACM0`，不是`radar_bench_test.py`/`calibrate_yaw_sign.py`默认的`/dev/ttyUSB0`（USB口枚举顺序不保证每次一样，跟问题13里"leishen_n10p_ws"那次验证用的`/dev/ttyACM0`一致）——每次连接雷达前建议先用`ls /dev/serial/by-id/`或`lsusb`确认实际端口，不要假设默认值一定对。

    **2026-07-08 决定：`yaw_sign` 真机标定优先级降低，暂不专门测**：讨论真机飞行标定方案时发现，`navigate()` 本身把 `yaw_pid` 目标固定设成0（主动把yaw摁住），实际飞行时yaw基本贴着0°(问题11观测到的真实yaw漂移只有2-5°量级)。`body_to_world_xy()`公式在`yaw=0`时`yaw_sign=+1`和`-1`算出来的结果完全相同，只有yaw明显偏离0时符号才会造成实质性差异——5°量级的误差换算到1m探测距离，位置误差大概几厘米，跟已知的15cm悬停随机噪声(问题8)是同一量级。**结论：`yaw_sign`标定的实际收益在当前飞行模式下不高，优先级降低，暂不安排专门的真机旋转测试**（也顺带不用纠结"T265旋转时坐标会不会偏差"这个问题，本身也没测过）。跟当年问题3(T265+光流融合)"没有实测证据支撑必要性，优先级排后面"是同一决策逻辑。如果以后飞行任务设计需要明显的yaw转动(比如原地转圈扫描找杆子)，需要回来重新评估这个优先级。

    **雷达用途的架构决策（2026-07-07，参考外部资料后确定）**：
    - **避障：确定用点云直接反应式方法，不用SLAM建图**。查资料确认这是业界常见分野——反应式导航(如VFH)每周期直接消费当帧点云判断决策，计算量小、响应快；SLAM建图虽然能给全局路径规划提供依据，但资料明确指出"构建出可用的障碍物地图需要几秒钟"，跟"1m内快速反应"这个时间预算不匹配。已有的 `get_obstacles()`(单帧空间聚类)+`PoleTracker`(多帧时间持续性) 本质上就是这个思路的实现，方向已确定不需要改。也实际验证过 `leishen_n10p_ws` 官方SLAM链路本身能正常跑（驱动+建图全部走通，`/dev/ttyACM0`+460800bps确认，跟`Lradar.py`测的背景墙数据吻合），只是不打算把它用在避障这条路上。
    - **定位：只是一个备用方向，是否采用取决于后续是否有数据支撑**——2D雷达只能提供水平面(x/y/yaw)信息，没有高度，即使做也不能替代现有的激光测距+光流那条高度链路。查资料显示"融合雷达+视觉+惯导优于单独用雷达里程计"，没有证据支持"2D雷达可以独立替代视觉惯导做定位"。**目前T265没有暴露出定位精度不够的证据**(已知问题都是冷启动检测/安装角度，不是精度问题)——跟当年问题3(T265+光流融合)的决策逻辑一致："没有实测证据支撑必要性，优先级排后面"。如果以后物理矫正完T265角度、仍然观察到具体的定位不够用场景，再重新评估要不要引入雷达辅助定位。

    **ubuntu-pi 上新增USB拓展坞(2026-07-07) — 已验证对雷达和T265均无实质影响**：板子(用户名`sunrise`，地平线旭日X3派/RDK X3)新接了一个USB拓展坞用于扩展外设连接。查资料确认这块板子官方设计本身就是"通过USB Hub扩展多路USB接口"，拓展坞是同一思路的延伸，可行；但资料也提到两条要点——(1) 拓展坞如果是无源(总线供电)可能让板子供电吃紧，官方要求用5V3A适配器供电；(2) **Intel RealSense类高带宽设备经USB Hub可能丢帧，待适配验证**——T265正好是这类设备，值得专门测。实测：雷达一开始"完全没数据"，排查后发现是笔者自己没清理干净之前SLAM测试残留的ROS2进程占用了`/dev/ttyACM0`，跟拓展坞无关，清理后雷达工作正常(361点/圈，聚类正常)。T265做了8秒和90秒两次采样：8秒那次显示186Hz、1次超时，看着像有问题，但90秒长采样显示平均198.3Hz(接近标称200Hz)，仅有的1次超时发生在第0.5秒(数据流刚启动的常见瞬态)，之后89.5秒完全没有>100ms的间隔——**修正结论：拓展坞对T265没有观察到实质性丢帧影响**，之前担心的"经Hub可能丢帧"这条警告在静止场景下没有被实测证实。

### 其他约定
- root 登录做的文件操作（`mkdir`/`mv`/`scp` 上传等）之后必须 `chown -R sunrise:sunrise` 改回属主
- `FJJ/.git` 是板载独立历史，不与本机仓库做 push/pull 关联，只用于板子上本地 `commit`/`checkout`/`reset` 回退
- 推送本机代码到远程用逐文件 `scp`，不用递归复制整个目录（避免带上 `__pycache__/`、`.ipynb_checkpoints/`）
- **`FJJ/.git` 里换行符约定不统一，scp 后提交前必须先核对**：`basic_radar/Lcode/Lradar.py` 是 LF，但 `basic_radar/Mission_GPT.py`/`main.py` 历史上就是 CRLF（板子仓库本身遗留的不一致，不是本机的问题）——本机 Windows 编辑器/git 存的文件基本都是 CRLF，如果不管三七二十一 scp 过去就 `git commit`，凡是原本是 LF 的文件会被换行符污染成假性全文件重写(`git diff --stat` 显示几百上千行改动，实际可能只改了几十行)。**流程**：scp 完先 `git show HEAD:<file> | file -` 看原来是不是 CRLF，跟 `file <file>` 比对当前工作区状态，不一致就用 `sed -i 's/\r$//'`(转LF) 或 `sed -i 's/$/\r/'`(转CRLF，注意不要对已有CRLF的行重复加，先转LF再统一转CRLF更保险) 按各文件原有约定改回来，再 `git diff --stat` 确认改动行数量级合理，才能 `git commit`
- **飞行测试数据要同步回本机仓库**：`ubuntu-pi` 上 `basic/test_data_*` 里归档的 `flight_data_*.jsonl.bak` 等测试数据，以后要同步一份到本机仓库对应位置（`drone_control/tools/test_data_*`），不要只留在板子上——之前 2026-07-06 的数据只在板子上，本机分析时要临时 ssh 上去现拉，之后应避免这种情况

- 任何"限定路径可做"及以上级别的操作，执行后立刻用只读命令验证结果，不假设命令一定成功
