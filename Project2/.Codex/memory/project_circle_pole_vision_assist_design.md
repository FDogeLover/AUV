2026-07-13讨论确定的circle_pole阶段2(双杆)视觉辅助方案，只是设计讨论，**代码尚未实现**。完整设计见`docs/superpowers/specs/2026-07-13-circle-pole-design.md`"阶段2视觉辅助方案"一节。

**两颗摄像头分工不同，不要搞混**：
- **前置1080p USB摄像头**：辅助判断杆塔方向（横向偏移），**不判断距离/远近**。已标定水平FOV≈82°，焦距≈1100px@1920宽（用已知宽度物体+已知距离的简易公式`tan(半角)=W/(2D)`反推，不是正式棋盘格标定，精度±2~3°量级）。
- **下置IMX219摄像头(CSI)**：辅助定位（识别地面标记/形状，很可能是赛题"实心黑色圆"降落点标识），**不是**颜色识别。硬件调通过程见[[project_imx219_camera_bringup]]。

**前置摄像头的简化机动设计（核心是"不判断远近"这个决定，避免了单目测距的精度问题）**：
- 摄像头朝+x方向，横向移动用+y，靠近/后退用x
- 不比较两根杆塔谁远谁近；绕完一根后退回x=0基准线，再对准另一根杆塔的y方向靠近，两次都是同样的"对准+靠近+环绕+退回"流程，不需要知道谁远谁近
- 像素偏移→方位角：`方位角=atan(dx_px/1100)`（dx_px=检测到的目标像素x - 画面中心960）
- **方位角→该往y移动多少，用闭环视觉伺服而不是算一次性位移**：把方位角(或dx_px)当PID误差量，目标设0(居中)，每次新拍一张图更新一次、输出y方向速度指令，持续修正到居中为止——不需要知道杆塔实际距离，跟现有`x_pid`/`y_pid`架构风格一致，是讨论时明确选定的方案(相对于"假设一个距离再算一次性位移"这个更不可靠的备选方案)

**讨论过但决定不采用的方案**：
- "先探测两根杆塔坐标再规划全局路径"——雷达有效探测距离~1m，探测阶段本身还是要贴近每个候选位置飞，省不掉这段路程；假阳性风险(circle_pole真机测试已验证发生3次)在"先规划再执行"模式下更难中途纠正。结论：继续用反应式设计(巡航中发现即环绕)，不改。
- 前置摄像头做单目测距(根据杆塔已知直径3.5cm反推距离)——理论可行但被"不判断远近"这个更简单的机动设计绕开了，不需要做。

**How to apply**：以后正式写视觉辅助代码时，直接按这个设计走，不用重新讨论方向选型；前置摄像头FOV标定值(82°/1100px)如果换了摄像头或镜头需要重新标定。

**2026-07-13下置摄像头色彩调试补充记录(下置摄像头本身已暂时搁置，回到circle_pole主线，这段留档供以后捡起)**：
- 排查"下置摄像头拍出来发蓝发青"，一路发现根因其实是拜耳解码排列用错了(`BayerRG2BGR`应为`BayerBG2BGR`)，详见[[project_imx219_camera_bringup]]，不是白平衡/光照的问题
- 修好排列后，用"黑电平校正(raw四通道各自算)+白平衡+百分位数自动拉伸对比度+饱和度提升1.35倍+双边滤波降噪+反锐化蒙版"这套手动流程，效果已经能接近前置UVC摄像头的观感（暖色调正常、细节可辨），脚本在`drone_control/tools/camera_test_20260713/process_imx219_v2.py`风格代码(尚未提交，只是ssh上验证过)
- 尝试借官方ISP直出(`/dev/video8`，NV12格式，`vs-isp0-2→vs-vse0-0`分支，理论上比手动flow更好)，结果卡死超时，`dmesg`显示`sif2 reset done`反复+`sif frame size incorrect, hsize count:0x0`，说明这条ISP分支从未与传感器正确同步过，需要`media-ctl`显式配置整条链路(`imx219→sif2→isp0-2→vse0-0→video8`)的格式/链接，工作量和不确定性都较大，**已决定暂缓**，跟之前放弃官方demo驱动栈(`hbn_vnode`)是同一类"官方ISP集成"問題，一并搁置
- **结论**：下置摄像头当前手动处理流程质量已经够用(能看清形状轮廓、颜色基本正常)，暂时搁置，回到circle_pole主线（阶段2双杆/land()闭环改进等）；以后如果真要深挖官方ISP，直接从`media-ctl -d /dev/media1 -p`里`vs-isp0-2`/`vs-sif2-0`/`vs-vse0-0`这几个entity的链路配置入手
