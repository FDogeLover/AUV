用户在排查无人机问题时表现出扎实的工程直觉：不会被动接受给出的假设/结论，经常会主动追问更简单的替代解释，也愿意动手做物理实测来验证（比如手持飞机做"抬起放下"测试来验证传感器/通信延迟，而不是只看代码分析）。

**具体例子（2026-07-05 会话）**：
- 我曾把"高度数值几秒后才追上真实变化"归因为"激光传感器响应滞后"，用户追问"这是否是传输导致的延迟，而不是传感器问题"——结果确实是通信代码里一个 `time.sleep` 位置放错导致的软件bug，不是传感器问题。这次追问直接推翻了一个原本看似合理但错误的结论。
- 用户会主动要求做最小复现测试（纯悬停+单独高度阶跃）来排除干扰变量，而不满足于混合运动测试里的模糊证据。

**Why:** 这说明用户不是被动接受分析结果的角色，而是共同排查问题的技术伙伴，容易发现过早下结论的漏洞。

**How to apply:** 汇报排查结论时，要主动区分"已证实"和"有依据但未证实的假设"，遇到多个可能解释时不要只挑一个讲，尽量都列出来并排优先级；当用户提出反向假设或追问替代解释时，要认真去代码里核实而不是简单辩护原结论，这个习惯在这次会话里帮忙纠正了一个错误方向（错误地怀疑传感器，实际是软件bug）。
