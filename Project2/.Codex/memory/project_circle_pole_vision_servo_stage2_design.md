**2026-07-14真机测试进展（同一天，实现完成后紧接着做的）**：
1. **摄像头连通性+HSV阈值现场标定**：前置USB摄像头实际是`/dev/video32`或`/dev/video0`(USB枚举顺序不固定，每次连接前要用`v4l2-ctl --list-devices`确认，不能硬编码假设)。红/绿杆塔实测颜色都比初始经验值暗得多、饱和度低得多——红色`S_min`从120下调到35，绿色更极端(远距离~5m时饱和度弱到跟背景完全混在一起，近距离~2m采样后才能正常分离，S_min最终定为25)，已现场标定并写入`HSV_RANGES`。顺带发现`PoleVision.start()`原来没显式设置分辨率，摄像头默认给320x240而`CAMERA_FOCAL_PX`(1100)是按1920宽度标定的，已修复(显式设MJPG+1920x1080)。

4. **首次真机验证纯视觉触发（第1次尝试）**：日志明确记录"视觉确认green杆塔，开始视觉接近"，触发逻辑本身工作正常，用户目视观察到飞机持续朝杆塔飞（视觉伺服居中+固定慢速前进在真机上确实生效）。**全程约30秒都没有出现"APPROACHING阶段雷达确认坐标"日志**——雷达始终没能确认出坐标，`_approach_pole_center`全程是`None`，纯视觉阶段一直没有被雷达接管。约30秒后雷达USB连接因飞行振动物理断开(详见[[project_n10p_radar_pole_test]])，级联触发飞控串口超时紧急降落——安全机制本身工作正常，是这次真实的硬件故障。

5. **第2次尝试：用户按计划人工接管，视觉伺服方向确认正确**——加固雷达接线后重飞，同样触发纯视觉APPROACHING，飞机持续朝杆塔飞了约47秒。**用户看到有效接近后按预定计划(先记着不让它真的环绕，观察到开始有效接近就人工接管)主动人工接管降落**，触发的"飞控串口超时2s紧急降落"是人工接管/断电的正常副作用，**不是硬件故障**——本次会话中曾一度把这个现象误判成"飞控UART的DMA request失败"导致的通信故障(dmesg里两次起飞都有`dw-apb-uart 34070000.serial: failed to request DMA`警告)，被用户纠正后确认那条警告大概率是无关的、每次起飞都会出现的良性日志，不是这次降落的真实原因——**排查硬件故障前，先问一句"是不是人工干预的"，不要看到"紧急降落"就默认是故障**。用户明确确认**视觉伺服y轴左右对准方向合理、居中方向是对的**，即`POLE_VISION_Y_SIGN=1`这个未标定的假设值实测正确，不用翻转。

6. **新设计缺口（用户决定暂不处理，靠人工接管兜底，记录供以后参考）**：纯视觉控制阶段(`_approach_pole_center`还是`None`时)没有任何自主距离上限——居中后固定慢速朝世界+x方向前进，唯一让它停下来的机制是雷达确认坐标后接管、飞到`APPROACH_CIRCLE_TRIGGER_DIST_M`(0.7m)触发环绕。如果雷达一直没确认（不管什么原因——比如断线，或者雷达本身效果不好/杆子太细/角度问题），飞机会一直往前飞没有自主刹车点，直到真的贴近杆子甚至撞上、或者视觉因太近丢失目标退回PATROL。当前策略是完全依赖现场人工监控+接管，不在软件层面加超时/次级距离保护。

**仍未验证的部分**：雷达坐标冻结后的距离阶梯控制、CIRCLING实际环绕触发与执行，两次真机尝试都是在纯视觉阶段(`_approach_pole_center`还是`None`)被中止/人工接管的，还没有观察到雷达接管+距离阶梯控制+CIRCLING这后半段链路在真机上的实际表现。

**2026-07-14 重要更正：上面这次"全链路成功"实际触发的是红杆子被误判成绿色，不是真的绿色链路**——用户事后反馈坐标(1.32,2.62)对应现场红杆子的物理位置，不是绿杆子(绿杆子从起飞就一直在视觉范围内，理应更早触发才对)。现场复现确认：单独把红杆子放在镜头前，`detect_target(colors=('red','green'))`报出的是`green`——根因是绿色HSV阈值(`hue 40~90, S_min=25`)太松，把背景(地面防潮布/柜子一带的低饱和度灰色区域，实测H集中80~95/S集中23~37/V集中137~172)的假绿色连通域(22309px)判成了比红杆子真实连通域(13094px)更大的目标，`detect_target()`的"面积最大者胜"逻辑因此选错。**已修复**：hue上限90收紧到75、S_min从25提到30(见`Lcode/pole_vision.py`)，同一张背景负样本图复测后`colors=('red','green')`正确返回`red`。用真实红/绿杆子(各自单独摆放)静态复测均正确识别，互不干扰。

**2026-07-14 新增PoleVision调试帧保存功能，用它揪出了第二个、更严重的干扰源：地面色块，不是墙面弱色偏**——`Lcode/pole_vision.py`新增`DRONE_VISION_DEBUG_DIR`环境变量，颜色首次检测到/切换时自动存一帧现场画面(`_save_debug_frame`)。修完HSV阈值后重新起飞验证绿色路径，结果**又触发了red杆塔**(坐标稳定复现在(1.02~1.06, 1.24~1.25)，两次独立飞行几乎完全一致)。调出调试帧才发现：画面里根本没有竖直杆子，是**地面上一块红色矩形标记(胶带/地标)+一块深灰/偏绿垫子**，平铺在地上，恰好落进红/绿HSV范围且连通域面积够大，被系统持续当成"杆塔"识别，真正的红/绿杆子这时候都还没入镜。**这不是阈值精度问题，是场地环境里有平铺色块干扰，跟"背景弱色偏"是不同性质的两个坑**——已让用户现场把这两块地面标记挪开/遮盖，之后需要重新测试确认排除干扰后能正确识别真正的杆子。**How to apply**：以后任何"颜色识别对不上预期"的排查，第一步就该用`DRONE_VISION_DEBUG_DIR`存帧看实拍画面，不要单凭日志坐标猜——这次连续两次靠日志坐标的"合理性"（跟已知红杆子位置对得上）差点导致误判成"又是HSV阈值不够紧"，实际图一开才发现追的根本不是杆子。**结论更新：至今没有一次真机测试是确认识别到、接近、环绕了竖直杆子本体的绿色路径**。红色路径的3次"成功"里，最早一次(坐标1.32,2.62)跟这次发现的地面红色标记坐标(1.02~1.06,1.24~1.25)相差较远(y方向差约1.4m)，更可能是真实红杆子；但后两次(坐标1.02,1.25/1.06,1.24)几乎精确重合在地面标记的位置，**大概率是重复追着同一块地面标记，不是真杆子**——这只是根据坐标距离的推测，没有对应的调试帧能证实第一次(1.32,2.62)那次画面里到底是不是真杆子(那次测试在加调试帧保存功能之前，没留下现场画面)。**How to apply**：排除地面干扰物后的下次测试，红色路径也要重新完整验证一遍，不能因为"之前红色测过看起来成功"就跳过复核。
