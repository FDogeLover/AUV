6. **高度控制异常 — 根因已定位并修复（通信层节流bug），修复效果待真实飞行验证**：2026-07-05 真机测试最早发现高度 setpoint 大幅变化时（比如0.5m/1.5m阶跃）实际高度几乎不跟随、且 setpoint 不变时也会缓慢自主"爬升"。排查过程中依次排除了倾角补偿假设（多次测试倾角全程<3.5°，数学上不够解释误差量级）、怀疑过光流模块激光传感器本身有固定偏差或响应滤波滞后（现场目测实际高度比日志高约0.3m，且用 `laser_height_monitor.py` 实测"抬起放下"确认了3-10秒的滞后）。

   **根因（已定位并修复）**：`Lcode/Lprotocol.py` 的 `listen_fc()` 里 `time.sleep(0.05)` 缩进对齐到 `while` 循环体，导致不管有没有解析到完整帧、每轮循环都强制睡50ms，把下行数据读取吞吐量限制在约20帧/秒，远低于飞控实际50Hz发送速率，造成下行数据（含激光高度、roll/pitch、光流速度等所有帧1字段）持续积压在串口接收缓冲区，`listen_fc()` 读到的其实是几秒前的旧数据——这不是传感器问题，是纯软件bug。**已修复**：sleep 改为只在真正空闲（`self.ser.read()` 超时无数据）时触发；`listen_start()` 加了 `reset_input_buffer()` 清理启动前残留的陈旧字节；发送/接收线程都加了 `serial.SerialException` 捕获+日志报警（原来串口异常会静默杀死线程，无任何提示）。**修复已用手持"抬起放下"测试验证滞后消失**。

   **这个bug大概率是高度异常和光流坐标对齐（问题2）相关性一直偏弱的共同根源**——光流速度和激光高度都走这条链路，如果存在秒级滞后，`analyze_of_t265_correlation.py` 的±5采样点(±250ms@20Hz)时延扫描根本补偿不了这么大的错位。

   **2026-07-06 真机验证：节流bug修复有效，高度阶跃测试通过**。同时发现并修复了另外两个独立问题，一并记录：

   - **状态机没有"到达后停留观察"机制**：原逻辑是 `dz < posthreshold_z`(20cm) 一满足就立刻切下一个航点，导致阶跃测试中高度从未真正稳定就已经在往下一个目标走。已在 `Mission_GPT.py`（`basic/` 和全功能版都改）加了 `arrival_hold_s=3.0` 强制停留时间，`arrival_timeout_max` 相应从 5.0s 加到 `5.0+arrival_hold_s`。修复后实测：1.5m/0.5m 阶跃都能精确稳定在目标±1cm（此前从未真正到达过目标就被切走）。
   - **起飞目标高度被硬编码默认值污染（已修复）**：`main.py` 里 `se_fc` 初始数组 `se_fc[5]`(com_z字段) 默认硬编码为 `120`(cm)，而 `Mission_GPT.py` 的 `takeoff()` 函数触发 `se_fc[2]=1`(task_sta，让固件执行一键起飞) 时，从未把 `se_fc[5]` 更新成本次航点真正的目标高度——飞控固件 `User_Task.c:155-156` 的一键起飞逻辑是直接用 `received_data.com_z` 当目标高度传给凌霄IMU(`OneKey_Takeoff(received_data.com_z)`)，于是不管 router.txt 设的是多少，实际起飞目标一直是残留的默认值120cm。2026-07-06首次测试时目标0.5m，起飞却冲到1.20m、15秒都没能收敛，验证了这个假设。**已修复**：`takeoff()` 里改成先把 `se_fc[5] = int(target_h_cm)` 写入、再触发 `se_fc[2]=1`。修复后重测起飞精确落在0.52m，问题消失。

   **仍待验证**：重新做一次X轴平移测试，重新跑 `analyze_of_t265_correlation.py` 看光流坐标对齐（问题2）相关性是否显著提升。

   **"当前高度"数据链路参考**（排查时用得上）：`pos[2]`/日志高度值来自**光流模块自带的激光测距传感器**，不是飞控自己的传感器也不是T265算出来的。链路：光流内部激光测距 → 串口帧 `0x34` → `Drv_AnoOf.c:155` 解析成 `ano_of.of_alt_cm` → `my_protocol.c:384` 原样打包进下行遥测帧 `buf[16-19]`（无校准/滤波）→ `Lprotocol.py` 解析成 `laser_height_cm` → `Mission_GPT.py:194` 覆盖进 `pos[2]`。`height_set()`（Kp=0.8/Ki=0.05/Kd=0.2, 限幅±30cm/s）算出的不是目标高度而是垂直速度指令，见 CLAUDE.md "飞控闭环控制"一节。

7. **一键降落/起飞指令可能被静默丢弃 — 只读代码推测，尚未最终确认；Python侧已加确认等待，固件侧重试仍未做**：2026-07-06 多次真机测试反复出现"程序日志显示降落/任务结束，但物理上没真正降落，靠人工遥控器手动降"。飞控固件 `LX_FC_Fun.c:135-151` 的 `OneKey_Land()`（以及 `OneKey_Takeoff`/`FC_Unlock` 等一整类一键指令）都是"`if (dt.wait_ck==0) 才发送，忙就直接放弃`"且**只在状态切换的那一个tick调用一次，不重试**（`User_Task.c` 里 `task_sta` 1→0 边缘触发块，调用完立刻清 `one_key_mission_f`）——如果那一个tick恰好有其他指令在等凌霄IMU确认，降落指令就会被无声吞掉。**注意**：曾经怀疑"飞机不稳定时CMD更容易撞车"，但读固件代码核实后已排除——`tar_setdata()`(`my_fun.c:2`)走的是 `dt.fun[0x41].WTS=1` 常规遥测帧通道，完全不经过 `dt.wait_ck`，飞行控制的持续数据流不会占用这个标志位；`dt.wait_ck` 的CMD通道本身还带重试(`ANO_DT_LX.c:476` `CK_Back_Check()`，每50ms重试一次最多5次≈250ms)。真正是什么导致具体某次 `dt.wait_ck` 非0，目前仍不确定，只是读代码推出的假设。**已修复的部分（Python侧，2026-07-06）**：`Mission_GPT.py` 的 `land()` 原本触发后立刻关串口退出，凌霄IMU定点悬停依赖的T265速度参考(`CMD 0x33`)因此在物理降落过程中直接断流——这部分已改成触发降落后不立即关串口，继续跑主循环轮询真实解锁状态(`re_fc[5]` unlock_sta)，确认已上锁(或`LAND_CONFIRM_TIMEOUT_S=10s`超时兜底)才真正关闭退出，`basic/`和全功能版都改了并同步到板子，真机验证待做。**仍未修复**：`OneKey_Land()`固件侧本身没有重试(涉及固件安全关键路径，需要讨论后再动手)。当前应对方式不变：每次自动降落都要人工盯着遥控器随时准备接管，不能完全信任程序自动降落。

    **2026-07-08 真实发生一次：一键降落无响应，人工遥控接管**——雷达悬停避障测试那次，全部航点飞完触发`land()`后，飞机**持续悬停没有任何下降反应**（不是"降落了但确认没传回来"，是确认过用户目视观察到飞机真的没动静），Python侧10秒后`LAND_CONFIRM_TIMEOUT_S`超时强制退出脚本，用户手动遥控器接管降落。`land()`本身没有记录任何遥测到飞行日志（不像`navigate()`每帧写JSON），所以事后没法从日志复盘这10秒里到底发生了什么，只能靠用户目击确认。这是问题7描述的风险第一次被**明确观察到物理层面确实没执行**（此前只有"日志说降落但没真降落"的说法，不能排除是确认环节的问题；这次排除了，是真的没执行），加重了"不能完全信任自动降落"这个结论的证据权重。

    **2026-07-08 发现并修复一个相关但独立的Python侧bug：`land()`等待循环没有清零速度指令**——用户进一步反馈，一键降落无响应期间飞机的坐标出现了明显偏差，跟`navigate()`时的稳定定点区别很大。查代码发现`land()`触发降落后只轮询`unlock_sta`等待确认，全程没有调用`set_speed()`——`se_fc[3]/[4]/[6]`(vx/vy/vyaw指令)停留在`navigate()`最后一次调用时的值(比如观察到的`v=(0,-2)`)，发送线程仍以50/100Hz原样重复发送这个过期指令长达10秒，且没有任何PID在持续修正，这正好能解释观察到的漂移。**这是跟固件侧一键降落丢帧完全独立的另一个问题**——即便固件那边执行正常，这个Python侧的gap也会在等待确认的窗口里让飞机带着一个陈旧速度指令漂移。**已修复**：`land()`等待循环里加了持续调用`set_speed(0,0,0,ramp)`清零水平速度、保持高度，`basic/`、`original/`、`basic_radar/`三个版本land()结构完全一致，一并修复并同步到板子，真机验证待做。

    **2026-07-08 新发现，比"确认超时"更值得警惕：`unlock_sta` 可能出现假阳性确认，Python认为已安全上锁并退出脚本，但电机实际没有自动停转**——Y轴步长测试那次，`land()`日志显示"降落确认：已上锁"（`unlock_sta` 读到了0，脚本正常退出），但用户明确确认：飞机当时确实已经落地/接近地面，但没有自动停转/上锁，是靠人工断电/上锁完成的。这跟此前"确认超时、强制退出"的模式完全不同——**这次脚本自认为任务安全结束了，实际飞机可能仍带电/半解锁状态**，风险更隐蔽：不会有报警日志提示需要人工介入，全靠操作者自己保持警惕。目前只有一次样本，无法判断是`unlock_sta`遥测本身偶发抖动误读成0，还是`FC_Lock()`确实执行了但电机没有响应停转指令，需要更多样本才能定位根因。**当前应对方式不变且更加必要**：不能仅凭"降落确认：已上锁"这条日志就认为可以离开，每次都要人工目视确认电机已停转、螺旋桨已静止，才能真正结束现场看护。

    **2026-07-10 首次同时捕获`unlock_sta`和`motor_pwm_mask`两个信号在假阳性确认瞬间的完整数据，坐实"两个字段互相矛盾"这一假设，问题21 `LAND_UNLOCK_CONFIRM_COUNT=5`去抖修复未能拦住这次误判**：`basic_radar`矩形航线到达确认耗时基线测试(6航点，见问题19相关记录)最后一段触发降落，日志显示"降落确认：已上锁"正常退出，但用户明确反馈**这次是靠人工接管完成降落，不是自动完成**。事后核对该次`land()`飞行日志(`drone_control/tools/test_data_20260710/flight_data_rect_arrivalbaseline_unlockfalsepositive.jsonl`)：确认退出前`unlock_sta`只有最后2条记录读到0，同一时刻**`motor_pwm_mask`全程稳定为15(四电机全部仍在出PWM)，包括判定"已上锁"退出的那一刻**——两个字段直接矛盾。由于`land()`内部轮询间隔(0.03s)比飞行日志写入间隔(节流后约0.06s)更密，不能排除5次连续确认在代码层面确实按`LAND_UNLOCK_CONFIRM_COUNT`触发了，但`motor_pwm_mask`全程未归零这一点是确凿的——**去抖修复本身可能语法上正常工作，但如果`unlock_sta`的假阳性本身能维持5次连续读数(~150ms量级)，去抖窗口就不够长**，且更根本地支持问题最初的猜测方向：凌霄IMU的解锁状态遥测(CMD 0x06)和电机PWM输出(CMD 0x20)可能真实存在短暂desync，不只是通信层的单帧噪声。**2026-07-10 已修复**：`land()`去抖判据从"只看`unlock_sta`"改成"`unlock_sta==0`且`motor_pwm_mask==0`同时满足才计入确认次数"，`motor_pwm_mask`为`None`(诊断数据不可用)时不阻塞，退化成只看`unlock_sta`的旧行为。`basic/`、`basic_radar/`各补了3个TDD单元测试，`original/`同步代码修改+`ast.parse`语法检查。三份已同步板子，见问题22后续记录（该修复本身仍有更深层假阳性未解决）。

    Fatal Python error: Aborted

    **这不是段错误(SIGSEGV)，是SIGABRT**(C++运行时`std::terminate()`被调用导致`abort()`)，且崩溃线程"没有Python帧"——说明是Python的`threading`模块完全不知道、管不到的纯C++线程，`fire_vision`的竞态假说因此被排除。`t265.py`的`stop()`其实已经是"先join `data_thread`再`pipe.stop()`"的正确模式，但`pyrealsense2`(librealsense)自己内部还有一层C++线程处理T265的USB通信，`pipe.stop()`调用返回不代表这些内部线程立刻彻底清干净——真正的C++对象析构发生在Python解释器退出、垃圾回收`self.pipe`这个对象的那一刻，时机不可控，跟解释器退出时其他模块的终结化顺序交织，很可能是`std::terminate()`的触发点。这跟已知问题1(T265冷启动检测失败)是同一条USB通信链路，本身就有已知的不稳定记录。
