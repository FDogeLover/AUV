# 空地协同智能消防系统（2023电赛G题）无人机侧设计 — fire_patrol

日期：2026-07-16
参考赛题：`D:\Competition\无人机\无人机培训\3、精通\2005-2023历年竞赛题目\G题_空地协同智能消防系统.pdf`

## 背景与范围

G题是无人机+消防车（4轮小车）的空地协同系统。**本设计只覆盖无人机侧**，新建 `drone_control/fire_patrol/`（以 `drone_control/basic/` 为模板）。消防车是完全独立的硬件/代码，本仓库不涉及；火情识别不用K230，改为树莓派本地跑OpenCV + 单个下视摄像头。

赛题任务：40dm×48dm巡防区域，无人机18dm高度全覆盖巡逻（垂直向下激光笔指示航迹），发现火情后接近确认→警示→降低到10dm悬停3s抛洒灭火包→坐标广播给消防车→继续巡逻→返航精准降落。发挥部分限时360s。

## 覆盖巡逻路径

40dm×48dm区域按8dm×8dm划分为**6列×5行=30个格心**的网格（题目3.1(5)"激光笔扫到8dm×8dm粗线框区域内某处即视为覆盖"），格心间距0.8m。本地坐标系原点(0,0,0)取T265上电点，物理上让起降点正好落在第1个格心（row0,col0）上，避免额外标定一个"起降点相对格网偏移量"的现场实测步骤。

**弓字形（boustrophedon）路径**，只在列两端格心转弯（不贴边飞到场地边界，转弯点就是格心本身）：

| # | x(m) | y(m) | 说明 |
|---|---|---|---|
| 起飞 | 0.0 | 0.0 | 本地原点 = row0/col0格心 |
| 1 | 4.0 | 0.0 | row0终点 |
| 2 | 4.0 | 0.8 | row1起点 |
| 3 | 0.0 | 0.8 | row1终点 |
| 4 | 0.0 | 1.6 | row2起点 |
| 5 | 4.0 | 1.6 | row2终点 |
| 6 | 4.0 | 2.4 | row3起点 |
| 7 | 0.0 | 2.4 | row3终点 |
| 8 | 0.0 | 3.2 | row4起点 |
| 9 | 4.0 | 3.2 | row4终点 |
| 降落 | 0.0 | 0.0 | 飞回原点降落 |

巡航高度Z=1.8m（对应赛题18dm要求）。5条车道横向覆盖40dm宽度，纵向沿48dm飞完；车道内连续飞行不逐格停留，只在10个转弯点做`navigate()`到达确认。

路径生成用脚本算出上表并写入 `fire_patrol/router.txt`（复用 `basic`现有的 `x,y,z`逐行格式），不手写。

## 状态机

```
IDLE → TAKEOFF → PATROL → [APPROACH → CONFIRM_WARN → HOVER_DROP] → PATROL(续飞) → LAND → END
```

沿用`basic/Mission_GPT.py`现有的`IDLE/TAKEOFF/LAND/END`及`navigate()`到达确认机制，新增`PATROL`(=原`NAVIGATE`改名)/`APPROACH`/`CONFIRM_WARN`/`HOVER_DROP`。

### PATROL

沿`router.txt`飞完10个转弯点，下视摄像头后台线程持续跑红色检测（不阻塞30ms主循环，风格与`listen_fc()`一致）。检测到红色光源且`fire_triggered==False`时：记录当前`target_index`（用于续飞），切`APPROACH`。**`fire_triggered`置`True`后，即使摄像头再检测到红色也不会重新进入这个分支——全程只响应一次**（题目发挥部分测试只点亮1个火源，符合场景）。

### APPROACH（视觉伺服对准正下方）

- 悬停锁定当前x,y，不再推进`router.txt`航点
- 摄像头检测到的红点像素中心先过滑动平均滤波，减少单帧噪声；连续多帧稳定后才计算一次修正量
- 独立的、比巡航`navigate()`更小的增益和更低的输出限幅（小步微调，不复用跨格移动用的`xylimit`），避免对准阶段大幅晃动
- 修正量死区（像素偏移小于阈值不修正，防止中心附近来回抖）
- **符号约定需要提前验证**：实现后先地面台架测试"红点偏移方向→无人机修正方向"是否正确，防止正反馈导致偏差越修越大（这类符号标定问题在本项目里有前车之鉴，见`docs/known_issues.md`雷达yaw_sign未标定问题）
- `APPROACH_TIMEOUT_S`（如10s）超时兜底：不强求完全居中，按最近一次最接近的位置直接进入`CONFIRM_WARN`
- 对准满足阈值后（水平偏移换算的实际距离 < 3dm，留量对应发挥部分(2)"灭火包需落在半径3dm圆形区域内"的精度要求）→ `CONFIRM_WARN`

### CONFIRM_WARN

点亮警示LED（占位接口`warn_led()`，硬件未就绪前打日志/GPIO占位），满足题目发挥部分(1)"识别确认后用LED指示灯示警"。

### HOVER_DROP

降到10dm悬停`HOVER_DROP_DURATION_S=3.0`（**新增独立常量，赛题写死的固定值，与`navigate()`到达确认用的`arrival_hold_s`无关，不随版本参数继承讨论变化**——`arrival_hold_s`是判断"是否稳定到达某航点"的通用参数，各版本可以不同；`HOVER_DROP_DURATION_S`是题目规定的业务悬停时长，两者语义和归属完全独立，实现时不能混用）→ 调用占位接口`drop_bag()` → 把火情场地坐标（本地坐标换算到赛场dm坐标）通过通信链路广播一次 → 恢复`PATROL`，从保存的`target_index`对应的**下一个未完成航点**继续飞（不退回触发点，不重新开始）。

### LAND

复用现有`land()`双确认逻辑，不改动。

## 通信协议（无人机→消防车）

物理链路：透明UART转无线模块，改造`original/Lcode/Lprotocol.py`的`Serial_dmz`类。帧内容从`cls/cnt`改为坐标+帧类型：

- **心跳位置帧**（1Hz，满足基本要求(3)"每秒1次位置坐标"）：帧类型=0，携带当前场地坐标(x,y)
- **火情帧**（一次性，`HOVER_DROP`阶段触发）：帧类型=1，携带火源场地坐标(x,y)

沿用`AA...FF`帧格式。坐标建议用cm整数（int16）而非dm，dm粒度(10cm)对消防车侧计算/显示巡逻航迹曲线和累计航程（基本要求(4)）可能偏"阶梯感"，cm精度更平滑，两者代价一样（都是2字节int16够用）。

## 参数继承

新版本先沿用`basic`的保守PID/到达确认参数，不用`basic_radar`/`circle_pole`的调优值（0.82/0.06增益、0.3s到达保持）——`APPROACH`悬停对准阶段优先要稳定性而非速度。等真机测试跑通整条链路后再评估要不要引入调优增益。

## 占位接口

`warn_led()`/`drop_bag()`：硬件（抛投机构、警示LED）均未就绪，先写函数签名+日志占位，GPIO映射留TBD，硬件到位后改动量最小。

## 设计审查：发现的欠缺项

汇总设计后逐条对照赛题要求和现有代码机制，发现以下此前讨论中未覆盖到的问题：

1. **误触发风险不可逆**：`fire_triggered`一次性闭锁机制下，如果巡逻过程中先被环境里其他红色物体（反光、其他队伍设备）误触发，真正的火源将永远不会再被响应，整个发挥部分（50分）直接清零。当前只做了"多帧稳定+滤波"防抖，没有专门区分"真火源"和"环境干扰红色物"。**建议**：加一层基于目标尺寸的过滤——按已知灯罩高度(<10cm)和当前巡航高度反推色块在图像中的合理像素面积范围，超出范围（太大/太小）不触发；现场测试时也要留意场地内有没有其它红色干扰源。
2. **检测线程健康检查缺失**：现有`listen_fc()`风格的后台线程都有隐含假设"线程一直健康运行"，但没有讨论如果视觉检测线程异常退出/摄像头掉线，主循环如何感知并降级处理（比如继续PATROL但不再响应检测，而不是卡在等待悬停指令的状态）。**建议**：给检测线程加一个心跳时间戳，主循环若超过若干秒未更新则记日志报警但不阻断飞行（保底跑完基本要求的巡逻+返航，放弃发挥部分）。
3. **抛投瞬间姿态扰动未评估**：抛投灭火包会瞬间改变无人机重量分布/配平，如果姿态波动较大有触发`angle_protect.c`30°倾角保护的风险（虽然30°容差较大，正常抛投不太可能触发，但没有专门验证过）。**建议**：`drop_bag()`调用后增加1-2秒纯悬停观察期再恢复`PATROL`，不要抛投完立即移动。
4. **对准阶段姿态水平度未纳入判据**：`APPROACH`靠像素偏移判断"是否居中"，隐含假设无人机姿态接近水平（roll/pitch≈0），否则摄像头视野中心并非严格垂直向下，会带来系统性偏差。当前只有`Attitude_Check()`的30°安全阈值，没有对精度层面的姿态水平做前置检查。**建议**：`CONFIRM_WARN`前增加一个轻量判据（如roll/pitch < 5°才算"真正对准"），提高对准可靠性。
5. **360s时间预算未验证**：发挥部分限时360s，当前设计未做时间预算估算（10个转弯点到达确认+悬停对准+3s悬停+续飞剩余航点+返航，参考`docs/known_issues.md`问题19"到达确认平均~4秒/段"的实测基线）。**建议**：写完实现后第一次真机测试就应该记录完整耗时，提前判断是否需要压缩`arrival_hold_s`等参数，而不是等到正式测试前才发现超时。
6. **"展示规划的巡逻航线图"要求未对应任何代码产出**：题目3测试要求(3)"开始测试前向评委展示含尺寸的巡逻规划航线图，方式不限"——这是纸面/演示材料要求，不一定需要代码支持，但可以顺便加一个小脚本把`router.txt`渲染成带尺寸标注的图（复用本次讨论生成的可视化），作为答辩材料，非必须但成本很低。

以上1-4项建议已经在"设计"正文里体现为具体机制（多帧滤波、超时兜底等），5-6项是待验证/待办事项，不影响本次实现范围，留待真机测试阶段处理。
