# 绕障飞行器（2020 TI杯D题）— 新版本设计

日期：2026-07-13

## 背景

赛题要求：无人机垂直起飞到150±10cm巡航高度，巡航中发现杆塔（红/绿两色），以50±10cm距离环绕飞行360°以上（红顺时针/绿逆时针），全部杆塔（2个，一红一绿）绕完后找降落点标识精准降落，全程≤5分钟，禁止无线通信/遥控，单按键一键启动。

现有代码（`basic_radar/`）具备：N10P雷达细杆检测（`PoleTracker`，世界系匹配）、点到点导航+到达确认（`navigate()`）、悬停避让（检测到杆子就停住等待）。**没有**：颜色识别、环绕飞行轨迹、视觉降落点定位、无线free的单键启动。

## 本次范围

只做控制流程本身：巡航搜索杆塔 → 雷达确认后环绕飞行 → 绕完预定数量的杆塔后飞到预设坐标降落。

**明确搁置，不在本次范围**：
- 颜色识别（LED/蜂鸣器提示、红绿判断绕飞方向）——方向参数预留接口，本阶段固定为顺时针
- 真实视觉降落点检测——降落点先用硬编码世界坐标常量，接口留出以后替换
- 去除无线依赖、单键启动——测试阶段仍走现有SSH流程，比赛前另行处理

## 阶段划分

**阶段1（本次实现目标）**：2m×1m量级小范围，单根杆子。
- 巡航路径简化为一条直线（如沿x轴走2m，y居中）
- 检测到杆子立即触发环绕，绕完这一根直接进入降落（不需要计数逻辑）
- 降落点用固定坐标验证 `TO_LANDING → LANDING` 链路能跑通
- 验证目标：`circle_planner`航点数学是否正确、`navigate()`到达确认在连续转向场景下的表现、状态机切换是否正确、悬停避让与环绕的互斥逻辑是否安全

**阶段2（阶段1真机验证通过后再做）**：4m×3m全场，双杆。
- 巡航路径换成S形，覆盖全区域（行间距按雷达命中率曲线取80cm量级，行数覆盖300cm宽度）
- 恢复"已绕数=2才转降落"的计数逻辑
- 阶段1、阶段2共用同一套状态机和`circle_planner.py`，只是`router.txt`航点和"杆塔总数"常量不同，逻辑不用重写

## 目录结构

`drone_control/circle_pole/`，以`basic_radar/`为模板复制（`main.py`/`Lcode/`全套）。改动集中在：
- `Mission_GPT.py`：状态机改造
- `router.txt`：阶段1用直线航点，阶段2换S形
- 新增 `Lcode/circle_planner.py`：只放"给定杆塔世界坐标+当前飞机位置，生成环绕航点列表"的纯函数，不依赖飞控/雷达对象，方便单独单元测试
- `Lcode/Lradar.py`（`PoleTracker`等）原样复用，不改

## 状态机

新增顶层状态：`PATROL → CIRCLING → TO_LANDING → LANDING`。

### PATROL
沿`router.txt`航点走，`pole_tracker.update()`照常轮询（`POLE_POLL_INTERVAL_S=0.5s`）。

**悬停避让保留、不关闭**：沿用`basic_radar`现成的`POLE_DANGER_DIST_M=0.75m`悬停避让逻辑——只要杆子进入"已确认"列表（`min_hits=3`）且距离<0.75m，正常触发悬停。这是巡航阶段防止撞上"还没决定要环绕"的杆子的安全网。

当`confirmed_poles()`出现一个**未绕过**的新杆塔（世界坐标去重，容差同`world_eps_m`），且当前不在`CIRCLING`态：
1. 保存当前patrol的`target_index`（用于恢复）
2. 记下该杆塔世界坐标为"当前环绕目标"，从悬停避让判断中排除它（其余未开始环绕的杆子仍正常触发避让——阶段2两杆场景下适用）
3. 调用`circle_planner.generate_circle_waypoints()`生成环绕航点，切换`self.targets`到这组航点，状态转`CIRCLING`

### CIRCLING
复用现有`navigate()`的到达确认机制（`arrival_hold_s`/滑动窗口）逐点飞完环绕航点。绕完后：
- 该杆塔标记为"已绕"（加入已绕集合，恢复悬停避让对它的正常判断）
- 恢复保存的`target_index`，状态转回`PATROL`
- 若已绕杆塔数达到预设总数（阶段1=1，阶段2=2），直接转`TO_LANDING`，不再继续剩余patrol航点

### TO_LANDING
飞向`LANDING_POINT`常量（世界坐标，占位值，需现场量出实际位置后改），到达后转`LANDING`。

### LANDING
调用现有`land()`。

## 环绕航点生成（`circle_planner.py`）

```
generate_circle_waypoints(center_x, center_y, cur_x, cur_y, radius=0.5, n_points=6, direction="cw", z=1.5)
```

- 从"当前位置到圆心连线与圆的交点"作为起始角度，避免先横穿到圆上任意一点
- 按`direction`（本阶段固定`"cw"`，参数预留给以后接颜色判断）每60°生成6个点
- **再追加第1个点作为第7个航点**，确保闭合一圈≥360°（否则6个点首尾不重合，实际只转了300°）
- 杆塔半径（~1.75cm）不额外补偿到`radius`，量级可忽略

## 已知限制（写入，不是本次要解决的问题）

**杆塔坐标定位精度可能撑不住50±10cm**：`PoleTracker.confirmed_poles()`聚类容差`world_eps_m=0.2m`，被判定为同一根杆子的多次命中点彼此世界坐标最大可差20cm，取平均后杆塔中心估计本身可能带±10cm量级误差。环绕半径基于这个估计中心计算，中心偏了的话实际绕飞距离可能超出50±10cm——这是雷达测杆塔位置的精度天花板，不是环绕算法本身的问题，没有视觉/更高精度传感器难以压低。阶段1目标是验证机制能否跑通，不是卡比赛精度指标，先照当前精度跑，实测数据出来后再评估是否需要收紧`world_eps_m`或引入其他修正。

**墙角/障碍物边缘误判风险**：`PoleTracker`区分"杆子候选"和"大障碍物"靠聚类点数（连续点云才算大障碍物被过滤），但墙角/边缘处雷达视角有几何不连续性，容易断裂成孤立小聚类，且和真杆子一样静止、稳定重复出现——现有算法**无法**从雷达数据本身区分"墙角伪影"和"真实细杆"。

缓解方式：依赖测试/比赛环境保证障碍物边缘离飞行路径>1.2m（雷达`max_range_mm`）来规避，不是算法层面的彻底解决。实际测试安排：网兜内的安全/静态测试空间小，墙很近，但真正验证环绕飞行的完整飞行测试在更开阔空间进行，届时墙体不在雷达探测范围内，风险可控。若以后比赛场地边界离飞行路径较近，需要重新评估。

## 测试计划（阶段1）

- 单元测试：`circle_planner.generate_circle_waypoints()`用不同`cur_x/cur_y`组合验证起始角度选取、闭合逻辑、点数正确
- 真机测试：小范围单杆，验证 PATROL 检测→CIRCLING 环绕→TO_LANDING→LANDING 全链路；观察环绕航点在真实到达确认下的耗时/精度，判断是否需要调整`radius`容差或`arrival_hold_s`
