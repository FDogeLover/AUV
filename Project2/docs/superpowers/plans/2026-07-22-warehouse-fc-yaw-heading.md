# warehouse_inventory 飞控 IMU 航向锁定方案

## 问题与目标

2026-07-22 两次 C 面实飞均在 C3 附近出现航向偏转。第二次完整日志显示：触发前约
5 秒 T265 yaw 变化约 9.2°，飞控下行姿态 yaw 同期变化约 4°；恢复阶段飞控 yaw 已对
`+3°/s` 指令产生约 1.3°响应，但 T265 yaw 仅改善 0.13°。这说明板间环境下 T265 yaw
不能继续作为可靠航向闭环反馈，否则错误视觉航向会主动生成转向指令。

目标：

1. 仓库任务默认使用飞控下行帧中的 IMU yaw（`re_fc[3] / 100`，单位度）锁存起飞航向并闭环。
2. T265 继续负责 XY 位置/速度，T265 yaw 只参与日志和双源一致性诊断，不再决定 yaw 指令、
   航向故障或恢复结果。
3. 正常航向修正默认限幅降为 `±1°/s`；保留角度回绕、1.5°死区、8°故障阈值及现有原地恢复/降落。
4. 飞控 yaw 数据未到达、持续过期、非有限数或不合理跳变时禁止起飞；飞行中发生则输出零 yaw，
   并在同一控制 tick 转入安全降落。
5. 日志必须同时保留 T265 yaw、飞控 yaw、实际反馈源、反馈年龄及“相对起飞方向的双源变化差”，
   便于区分视觉漂移和真实机体旋转。

## 方案选择

采用“飞控 yaw 单源闭环 + T265 yaw 旁路诊断”。不采用以下方案：

- 调高 T265 故障阈值：只能推迟保护，无法阻止错误视觉反馈主动转动机体。
- 简单关闭 Python 航向保持：只能形成零角速度命令，不能锁定绝对起飞航向，并会失去现有航向故障保护。
- T265/飞控 yaw 加权融合：两套 yaw 的零点、漂移机制和可信度不同，当前没有足够真机数据确定安全权重。

保留 `DRONE_HEADING_SOURCE=t265` 作为显式回退；默认值改为 `fc`。

## 改动范围

### `warehouse_inventory/Mission_GPT.py`

- 增加 `DRONE_HEADING_SOURCE=fc|t265` 解析，默认 `fc`。
- 增加原子读取飞控 yaw 的帮助函数：在现有 `Lcode.global_variable.lock` 内一次性读取 yaw、
  有效帧 `monotonic()` 时间戳和帧计数，并做有限值、年龄和跳变检查。上一次有效 yaw/
  帧号只由 Mission 控制线程维护，不由串口线程并发修改。
- 起飞解锁前同时读取 T265 与飞控 yaw；飞控源不可用时不解锁并进入现有安全降落路径。
- 解锁前至少要求串口线程累计收到 5 个有效关键帧；首个 Mission 读数只建立跳变基准，
  不与默认 0°比较。T265 与飞控 yaw 的绝对零点不同，解锁时不按绝对差拒绝，只记录各自基准。
- 将 `arm/update/recovery_status/clear_fault_preserving_target` 的输入统一经过航向反馈选择函数。
- 飞控源模式下，T265 confidence 只继续约束位置导航；航向控制有效性由飞控帧新鲜度决定。
- 飞行中飞控 yaw 失效时，当前 tick 先清零 yaw/XY，并直接把状态置为 LAND；不等待下一轮异常。
- 恢复期间适用同一失效规则，立即中止恢复并 LAND。LAND 中若 FC yaw 不可用，则只把 yaw
  指令清零并继续下降/上锁，绝不因航向诊断阻断降落。
- 在 TAKEOFF、NAVIGATE、SCAN、LAND 日志中补充：
  `heading_source`、`heading_feedback_age_s`、`heading_t265_delta_deg`、
  `heading_fc_delta_deg`、`heading_source_disagreement_deg`。

### `warehouse_inventory/Lcode/heading_hold.py`

- 保持公共控制器及 `DRONE_HEADING_HOLD_MAX_DPS` 的默认上限为 `2°/s`，避免改变其
  runaway 检测语义；仅在 Mission 选择飞控 yaw 作为反馈源时，把正常控制输出额外限幅为
  `±1°/s`。显式回退 T265 时仍保留原控制器行为。
- 控制器仍接收弧度，Mission 层把飞控度数明确转换为弧度，避免改变公共控制器数学语义。

### `warehouse_inventory/Lcode/Lprotocol.py` 与 `global_variable.py`

- 下行关键帧 yaw 明确为协议中的有符号 `int16 × 0.01°`。读取后无论原值位于哪个等价角度，
  Mission 均通过 `wrap_degrees` 归一化到 `[-180°, 180°)` 再转弧度。
- 串口线程在同一个 `lock` 临界区内同时提交 `re_fc`、`fc_last_rx_monotonic` 和
  `fc_frame_counter`，避免“新 yaw + 旧时间戳”的撕裂快照；原有 wall-clock 时间戳继续供
  全局串口超时使用。

### 测试

- 默认源为 FC，显式 `t265` 回退仍可用。
- 起飞锁存飞控 yaw 而非 T265 yaw。
- 相同 T265 yaw、不同飞控 yaw 时，指令只随飞控 yaw 变化。
- T265 yaw 漂移但飞控 yaw 不变时，yaw 指令保持零且不触发航向故障。
- 飞控 yaw 回绕（179°/-179°）方向正确。
- 飞控帧缺失、过期、NaN或异常跳变时禁止起飞/飞行转 LAND，且在进入 LAND 前清零控制指令。
- 首帧只建立基准且不误判；解锁前少于5帧时不解锁。
- 飞控 yaw 有效而 T265 confidence 低时，航向控制仍按 FC yaw 工作，但 XY 仍按原逻辑暂停/降落。
- 覆盖恰好0.5秒年龄、连续3个失效tick、恰好10°/超过10°跳变、恰好8°故障阈值。
- 覆盖 `179° -> -179°`、`-180°`边界；协议为有符号int16，不存在合法360°原始值。
- 恢复阶段使用飞控 yaw 判断改善，不受 T265 yaw 漂移影响。
- 双源相对变化差写入 NAVIGATE、SCAN、LAND 日志。
- 原有扫码 worker 隔离、航向恢复、返回和降落测试保持通过。

## 安全边界

- 飞控 yaw 来自 50Hz 下行关键帧；新鲜度使用串口接收线程写入的 `time.monotonic()`，
  最大可接受年龄设为0.5秒。过期需连续3个Mission控制tick才判失效，避免调度毛刺；总反应时间
  仍小于约0.6秒，远小于全局2秒串口超时。
- 单次相邻“不同帧号”的有效读数回绕后跳变超过10°视为传感器/协议异常，首帧只建立基准；
  跳变不尝试纠偏，立即走安全降落。
- 正常控制仍限幅 `±1°/s`；8°后才允许进入现有原地恢复，恢复仍受 3 秒、20°和无改善判据限制。
- 2026-07-22 首次 FC 源高度测试确认飞控下行 yaw 的数值方向与 yaw 指令正方向相反：
  `+3°/s` 恢复期间 FC yaw `20.89° -> 20.27°`，T265 yaw `3.71° -> 3.29°`。
  因此 FC 源只在最终发送端将正常和恢复指令乘以 `-1`；T265 回退模式及原始诊断角度不反转。
- LAND/END/emergency 的清零与上锁顺序保持不变。
- FC反馈失效日志记录原始值及 `not_ready/stale/non_finite/jump` 原因。
- 不在本次代码交付中自动起飞；板端仅运行单元测试。

## 验证与回退

1. 本机定向测试和 `warehouse_inventory` 全量 pytest。
2. C 面实飞日志离线回放：验证同一 T265 漂移轨迹在 FC 源下不会错误触发 `+1/+2/+3°/s`。
3. Qoder 计划审查与实现 diff 复审。
4. 同步板端、核对 LF/SHA256、运行关键回归测试。
5. 真机先做无货架高度阶跃，再决定是否重测 C 面；每次起飞前重新确认现场安全。
6. 如 FC yaw 路径出现异常，可显式设置 `DRONE_HEADING_SOURCE=t265` 回到旧反馈源，或 Git 回退本次独立提交。
