# warehouse_inventory 航向恢复与 SCAN 日志方案

## 问题与目标

2026-07-22 C 面实飞在 C3 扫码悬停及随后的 `1.25m -> 0.85m`
下降中，yaw 误差增大到 `8.19deg`。现有 `HeadingHoldController`
将该阈值当作锁存故障，立即输出 `0deg/s`，后续任务仍继续 XY
航行和扫码，导致绝对航向控制丢失。同时 `flight_data.jsonl` 没有
SCAN 控制 tick，恰好缺失 C3 扫码期间约 2 秒的关键数据。

目标：

1. `8deg` 从“清零 yaw 并继续任务”改为“停止 XY/暂停扫码并原地纠偏”。
2. 恢复阶段使用有界 `3deg/s` 输出；误差先进入 `2.5deg`，
   之后连续 1 秒不超过 `3deg` 才继续，形成迟滞防抖。
3. 最大纠偏连续 1 秒后误差未至少改善 `0.5deg`、3 秒未恢复，
   或误差达到 `20deg`，均终止任务并转入现有受控降落。
   恢复期间 T265 置信度低于定点门槛时，不允许继续发送恢复 yaw，
   直接转入降落。
4. 整次任务只允许一次恢复成功；第二次触发直接降落，防止
   “恢复—继续—再恢复”循环。
5. NAVIGATE 和 SCAN 使用同一飞行 tick 日志字段，不再出现扫码期间空档。

## 方案选择

不单纯放宽 `8deg` 阈值，也不在故障后继续 XY 航行。采用任务层
恢复子状态：底层航向控制器仍负责误差、回绕和有界指令；任务层负责
停 XY、保持触发时高度、计时、恢复门槛和降落决策。这避免把路线/扫码
状态写进通用航向控制器。

## 改动范围

- `Lcode/heading_hold.py`
  - 增加恢复输出和显式清除软故障的纯逻辑接口。
  - 保持原始航向目标，恢复成功时不重新锁定当前偏转航向。
- `Mission_GPT.py`
  - 增加恢复计时、稳定计时、触发高度和恢复结果。
  - 恢复期间固定 `vx=vy=0`，不推进航点、不累计超时。
  - 恢复失败转 `LAND`。
  - 抽取 NAVIGATE/SCAN 共用的飞行 tick 日志。
- `Lcode/inventory_controller.py`
  - SCAN 中触发恢复时，立即通过 generation 递增隔离当前 QR worker
    的迟到结果，并设置协作式 cancel event；飞行线程不等待 worker。
  - 旧 worker 未退出时绝不启动新 worker，继续 XY 零速保高；到恢复
    硬截止时间仍未退出则降落。旧 worker 退出后，恢复成功才从
    同一航点重新到位和扫码。
- 单元测试
  - 软阈值不再造成无纠偏输出。
  - 恢复期间停 XY/保高/不推进航点。
  - `3deg + 1s` 恢复、`3s` 超时和 `20deg` 硬降落。
  - 最大纠偏 1 秒无 `0.5deg` 改善则提前降落。
  - 恢复期间 T265 低置信度时 yaw 必须清零并降落。
  - 第二次恢复触发降落，且 `2.5deg/3deg` 迟滞窗口任一越界即重置。
  - SCAN worker 取消与旧结果隔离。
  - SCAN 日志含 yaw/指令/高度/航向恢复字段。

## 风险与回退

- `3deg/s` 只能在 XY 已停止的恢复子状态使用，正常任务仍为
  `2deg/s`。
- 方向错误或控制权威不足时，`20deg`/3 秒门槛必须保证有界结束。
- 恢复期间不允许扫码副作用晚到并改写仓位结果。
- QR 取消不依赖 Python 强制终止线程；安全性依赖 generation 令牌
  隔离副作，资源安全性依赖“旧 worker 退出前不重启”。
- 保留 `DRONE_HEADING_HOLD=0` 整体回退；代码可通过 Git 回退本次独立改动。

## 验证

1. 航向控制器、导航、SCAN、盘点状态机定向回归。
2. `warehouse_inventory` 本机全量 pytest。
3. Qoder 实现安全审查。
4. 同步板端后跑关键回归；不在本次代码交付中自动起飞。
5. 下次真机先执行无货架高度阶跃，每次起飞前重新确认现场安全。
