# Qoder Workflow Skill

ZCode × Qoder 双轮协作流程，适用于新功能开发和大规模重构。
最大审查轮次：2轮（Plan Review + Implementation Review）。

---

## 前置检查

收到指令后，立刻用 TodoWrite 创建完整任务列表：

```
[待办] Step 1: 生成结构化计划文档
[待办] Step 2: Qoder Plan Review（第一轮审查）
[待办] Step 3: 风险决策检查点
[待办] Step 4: 实施代码改动
[待办] Step 5: Qoder Implementation Review（第二轮审查）
[待办] Step 6: 输出最终结论
```

---

## Step 1 — 生成结构化计划文档

根据 `$ARGUMENTS` 描述，生成以下结构的计划文档，**保存到 `.zcode/plans/<功能名>_plan.md`**：

```markdown
# 计划：<功能名>

## 问题描述 & 目标
<清晰描述要解决什么问题，期望达到什么效果>

## 方案选择
| 方案 | 优点 | 缺点/风险 |
|------|------|----------|
| 方案A | ... | ... |
| 方案B | ... | ... |

**选择方案X，理由：<说明>**

## 改动范围
受影响的文件/函数/接口（逐一列出）：
- `文件路径` — 改动说明
- ...

## 风险点
- 安全隐患：<飞行安全相关风险>
- 边界条件：<极端情况处理>
- 回退方案：<如果出问题怎么回退>

## 验证方式
- 单元测试：<哪些测试覆盖>
- 桌面测试：<离线验证方法>
- 真机验证：<飞行实验设计>
```

文档生成后，将内容展示给用户并询问："计划文档是否需要补充？确认后进入 Qoder 审查。"

等待用户确认后再进入 Step 2。

---

## Step 2 — Qoder Plan Review（第一轮）

用 Bash 调用 Qoder，传入计划文档全文：

```bash
"C:\Users\FJJ\.qoder-cn\bin\qoderclicn\qoderclicn.exe" -p "
你是无人机软件架构审查员。以下是一份新功能计划文档，项目背景：
- 真实飞行无人机，代码缺陷可能导致坠机
- Python 上位机 + STM32飞控 + T265 视觉里程计
- 任务状态机驱动，降落安全是最高优先级

请审查计划文档，每条问题按以下格式输出：
[高风险] 问题描述 | 位于计划的「xxx」部分
[中风险] 问题描述 | 位于计划的「xxx」部分  
[低风险] 问题描述 | 位于计划的「xxx」部分
[通过]   整体评价一句话

重点检查：
1. 安全关键路径（降落/解锁/紧急停止）是否有遗漏
2. 方案是否存在未考虑到的边界条件
3. 改动范围是否完整（有无遗漏的联动模块）
4. 回退方案是否可操作

计划文档内容：
$(cat .zcode/plans/<功能名>_plan.md)
"
```

将 Qoder 输出完整展示，然后解析输出，统计各风险等级数量。

---

## Step 3 — 风险决策检查点

根据 Qoder 输出按以下规则处理：

**[高风险] 条目存在：**
- 逐条列出所有高风险问题
- 明确问用户："以上高风险问题如何处理？请选择：A) 修改计划后重新审查  B) 接受风险继续  C) 放弃本次改动"
- 等待用户明确回复后继续

**只有 [中风险] / [低风险] / [通过]：**
- 列出中风险条目并说明 ZCode 的处理判断（是否影响方案）
- 低风险记录在案，不阻塞流程
- 自动推进到 Step 4

**Qoder 连续两轮仍有高风险（重新走 Step 2 一次后仍有）：**
- 停止循环，告知用户："方案本身需要重新设计，建议回到 Step 1 重写计划。"

---

## Step 4 — 实施代码改动

按确认的计划方案实施。**每完成一个文件的改动，对照计划的"改动范围"自查一次**：
- 改动是否在计划范围内？
- 有没有引入计划外的修改？

实施过程中如发现计划有重大偏差（不是小细节），停下来告知用户再继续。

完成后运行项目现有测试：
```bash
cd drone_control/warehouse_inventory && python -m pytest -x -q 2>&1 | tail -20
```
测试全部通过后进入 Step 5。如有测试失败，先修复再进 Step 5。

---

## Step 5 — Qoder Implementation Review（第二轮）

获取本次改动的 diff：
```bash
git diff HEAD -- <改动涉及的目录>
```

调用 Qoder 做实现核查（角色是"对照计划查偏差"，不重新评审计划）：

```bash
"C:\Users\FJJ\.qoder-cn\bin\qoderclicn\qoderclicn.exe" -p "
你是代码实现核查员。你的任务是对照原始计划检查实现是否符合预期。
不要重新评审计划本身的合理性，只关注实现层面。

请检查：
1. 实现是否覆盖了计划中所有「改动范围」里列出的文件/函数
2. 有无新引入的逻辑错误（计划中没有的 bug）
3. 有无遗漏（计划要求做但代码里没有的部分）
4. 异常处理是否完整

输出格式：
[实现符合计划] 简短总结
或
[存在偏差] 偏差1：<描述>  偏差2：<描述> ...

原始计划摘要（改动范围部分）：
<从 .zcode/plans/<功能名>_plan.md 提取改动范围>

实现 diff：
$(git diff HEAD -- <目录>)
"
```

---

## Step 6 — 最终结论

根据第二轮结果：

**[实现符合计划]：**
- 总结本次改动：功能描述 / 改动文件列表 / 测试状态
- 提示用户："改动已通过两轮审查，可以 commit 并 scp 上板。上板前记得运行 /qoder-preflight。"

**[存在偏差]：**
- 列出偏差项
- 按偏差描述修正代码（不触发第三轮 Qoder，ZCode 自行修正后自查）
- 修正完成后输出最终总结

---

## 注意事项

- 计划文档保存路径：`.zcode/plans/`（已在 `.gitignore` 外，会被 git 追踪）
- Qoder CLI 完整路径：`C:\Users\FJJ\.qoder-cn\bin\qoderclicn\qoderclicn.exe`
- 审查轮次上限：2轮，超出停止循环
- 高风险决策权归用户，中/低风险 ZCode 可自行判断
