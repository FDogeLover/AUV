2026-07-23，确定在稳定版本`drone_control/basic/`之外维护独立的
`drone_control/competition_2026/`备赛版本，避免把未确定的比赛功能直接叠加到稳定飞行版本。

**赛题方向判断**：更可能是固定安全点位、点位内容或任务要求临场随机，而不是高精度
抓取钢球、向细管投放或首次遍历未知障碍。优先准备“两次飞行”模式：第一次遍历点位并
回传信息，人工判断关键点；第二次按选择结果复访或执行任务。保留空地协同可能，但使用
统一点位模型兼容无人机和小车，核心字段为`point_id`、位置、停留时间、动作和可选执行者
（UAV/CAR），不为小车复制整套任务系统。

**当前实现**：`competition_2026`已有`scout`与`execute`两阶段任务规划，支持配置化点位、
顺序、停留时间、动作和无硬件航线预览。航点编号及动作已进入飞行状态机，并通过后台事件
队列记录接近、到达、停留、动作请求/完成和离开事件；任务会话用于保存两次飞行的计划、
结果、事件和截图目录。截图、识别、存盘及界面逻辑不得阻塞飞控控制线程。

**图传决策**：保留两种可替换方案：(1) 成品图传接收器经HDMI/CVBS转UVC采集；
(2) 不同开发板在同一局域网内传输RTSP/RTP/UDP等数字视频流。普通图传直接接显示器只能
观看，若要程序截图，必须通过UVC采集卡或其他方式取得解码后的视频帧。

**地面站决策**：可以采用Foxglove，但不引入ROS。Python程序通过Foxglove SDK或兼容的
WebSocket服务发布视频、位置、状态、航点事件和任务计划。建议通道包括`/camera/video`、
`/drone/pose`、`/drone/status`、`/mission/events`、`/mission/plan`和
`/mission/command`。界面采用左右分屏，一侧实时视频，另一侧显示状态、地图、关键点选择
和第二次任务操作；比赛专用操作通过Foxglove Extension自定义面板实现。

**显示硬件约束**：开发板端显示完整Foxglove时，应使用能够运行Chromium的Linux开发板
以及HDMI、MIPI-DSI或USB显示屏。淘晶驰、迪文、Nextion等普通UART串口屏不能运行
Foxglove，也不适合实时视频，只能作为状态和按钮辅助面板。急停、解锁等安全控制不应只
依赖与视频共用的网络链路，应保留独立短距离通信或物理控制通道。

**当前实现完成度**（2026-07-23）：航点事件总线、任务会话、航线规划、自动截图、
视频接口+OpenCV/UDP-JPEG后端、机载视频生命周期管理、航点动作执行器、飞行前检查、
任务结果跟踪、无人机-地面UDP链路以及GPIO LED优先级租约均已实现并通过测试。
配置文件默认关闭所有可选功能，硬件确定后启用。

**后续顺序**：实现无ROS的Foxglove WebSocket网关及任务面板；最后补场地标定、坐标转换、
电子围栏、通信心跳和失联处理，并依据正式题目决定是否接入小车和自动视觉识别。

**安全约束**：当前配置中的点位坐标仅是占位或台架测试值，不可直接用于正式场地真机飞行。
真机测试前必须复核坐标轴、飞行边界、高度、返航、降落、急停和失联保护。
