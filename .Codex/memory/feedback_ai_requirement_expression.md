2026-07-23 总结：AI实现代码不难，难在它不知道系统约束、上下文和"不能做什么"。

## 核心原则

**说问题，不说解法**
低质量：「把到达判定改成滑动窗口，need=15, ratio=0.6」
高质量：「当前严格连续帧在T265噪声下达标帧只有30~40%，航点全靠超时跳过，需要改成容噪的判定方式」
说问题让AI选择合适实现；说解法则把你方案的局限性一起带进去了。

**把约束前置，尤其是"不能做什么"**
最有价值的注释不是"做了什么"，而是"为什么不那样做"。
需求模板：
```
背景：[系统正在做什么]
目标：[需要实现什么行为]
约束：
  - 不能做X，因为Y
  - 必须做Z，因为W
安全边界：[最坏情况下允许的行为]
```

**描述接口契约，不是伪代码**
描述"输入输出、生命周期、状态分类"，不要写伪代码让AI照着实现。
你的伪代码有缺陷，AI不会质疑，会直接实现。

**带着调试场景一起说**
「需要在日志里记录每帧到达判定结果和不达标原因」——不说，AI只实现功能本身。
调试时才发现日志是空的，是这个代码库真实踩过的坑。

**引用已有模式**
「参照heading_hold.py的degraded/fault双状态设计，给雷达连接状态做同样的分层」
好处：生成代码风格一致，且这个模式已在真机验证过。

**分离"必须正确"和"可以占位"**
明确告诉AI哪些是安全关键路径（解锁逻辑、降落确认、急停触发链路），让它在这些地方多花精力，不要均匀分配注意力。

## 对本项目的具体应用

给新功能需求时，先说清楚：
1. 这个功能在飞行哪个阶段生效（TAKEOFF/NAVIGATE/LAND）
2. 与`se_fc`/`re_fc`的交互方式（读还是写，加锁位置）
3. 失败时的fallback行为（是急停还是降级继续）
4. 需要记录哪些日志字段供事后分析
