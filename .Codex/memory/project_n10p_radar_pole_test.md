2026-07-07 台架测试（不装机，雷达单独通电）结论，为"水平面杆子绕行"功能新增的 `drone_control/basic_radar/` 相关。详见项目 CLAUDE.md 已知问题第13条。

**已验证通过**：角度基准(0°→机体+X，90°→机体-Y，已写入 `Lcode/Lradar.py`)、平板测距精度(±3cm内)。

**核心发现**：同一根细杆子摆在同一大致方位，65cm/30cm/45cm三次测试，命中角度每次都不一样(170/171/178° → 170/171° → 179°)，距离读数有时准(±3cm级)有时完全跟丢(偏差几十厘米，甚至没跟踪到从65cm移到30cm这个变化)。已排查确认不是数据阻塞/跨进程缓存伪影(每次都是全新进程+全新串口连接)，是真实的杆子回波，只是测距本身不稳定——推测是TOF雷达对细长目标的"混合像素/边缘效应"，扫描线打中心准、擦边就失真。

**命中率-距离关系(2026-07-07补充测试)**：命中率随距离下降规律清晰——70cm约90%，1m约70%，1.55m骤降到10%。**可靠有效探测距离上限大概在1m左右**，超过1m命中率急剧恶化。这是目前最重要的工程数字，直接决定绕障算法能规划出多少反应距离。

**调雷达参数提高命中率——已查证不可行**：翻过协议文档和ROS驱动源码，没找到"设置转速"或"启用双回波"的命令格式，只有电机启停两条指令有文档。唯一确认有效的办法是让目标物理上更近，不是调雷达内部参数。

**参考镭神官方SLAM包(`D:\Competition\自组无人坤\雷达\leishen_n10p_ws`)后确认的方案：空间聚类 + 多帧时间持续性组合，已用真实数据验证有效**：官方 `obstacle_detector.py` 用"角度维度空间聚类"(相邻点距离<eps同一簇，簇内点数<min_samples整体丢弃孤立噪声)识别大障碍物。移植到 `Lcode/Lradar.py` 的 `Serial_radar.get_obstacles()` 后发现：这个方法能干净分出大障碍物/背景墙，但**细杆子单帧通常只产生1个孤立点，天生凑不够min_samples≥2的门槛**，会跟噪声一起被误杀——空间聚类只解决"大障碍物vs噪声"，解决不了"细杆子vs噪声"。

真正管用的是加上时间维度：新增的 `PoleTracker` 类先用聚类排除大障碍物，剩下的孤立候选点记入滑动窗口，同一角度/距离附近重复出现次数达标(`min_hits`)才判定为确认的杆子——噪声不会重复出现在同一位置，杆子会。**真实数据验证**：1m处杆子，10次轮询里8次在359-360°附近重复命中，5个各只出现1次的噪声候选全部被正确排除，确认结果 `angle=359.6°, distance=969mm(误差-31mm), hits=5`。

**How to apply**：绕杆避障算法应该用 `PoleTracker`（而不是原始 `get_nearest()`/单帧 `get_obstacles()`）作为雷达侧的候选确认信号源。用户明确约束：只需要1m内的探测范围（这个范围命中率70-90%，够用），实际运行时无人机会沿路径主动搜寻杆子而不是指望远距离静态探测，后续会加视觉辅助——`PoleTracker` 定位是"雷达侧候选信号"，不是唯一探测手段，要跟视觉配合。规划绕障反应距离时按1m左右的可靠探测上限设计，不要假设能在更远处稳定发现障碍物。

**尚未验证的飞行动态干扰(2026-07-07提出)**：振动(电机/桨叶转动晃动雷达本体)这一项还没测，建议先做"拆桨接电+雷达固定"的台架振动测试。

**2026-07-07 真实飞行验证：`PoleTracker`未能复现台架效果，根因是几何方位角摆动，不是yaw漂移**——首次在真实飞行中测(杆子在起飞点180°/1m处，飞机飞向-0.6m留0.4m安全距离)，35秒全程"180°确认"的距离稳定在1.44-1.45m不随接近而变化，说明抓到的是背景墙不是杆子，真杆子信号淹没在噪声候选里没攒够`min_hits`。排查：yaw漂移只有3.08°(在4°容差内)不是主因；用实际轨迹反算杆子真实方位角，起飞点180°→接近后变成161°，**摆动了19°**，远超4°容差——根因是飞机接近目标同时有Y方向偏移(跟问题11的Y漂移同一现象)，目标不严格在正前方时，越接近方位角摆动越剧烈，纯几何效应。**这不是调大容差能解决的**(19°摆动没法用固定容差覆盖，会牺牲抗噪声能力)，真正修复需要用飞机自身位置变化实时重算目标应该在哪个角度，超出简单调参范围，暂未动手。

**雷达用途的架构决策(2026-07-07，查外部资料后确定)**：
- **避障：确定用点云直接反应式方法(现有get_obstacles()+PoleTracker思路)，不用SLAM建图**。查资料确认业界常见分野——反应式导航(如VFH)每周期直接消费当帧点云，计算量小响应快；SLAM建图能给全局路径规划提供依据，但资料明确"构建可用障碍物地图需要几秒钟"，跟1m内快速反应的时间预算不匹配。也实测验证过官方SLAM链路(`leishen_n10p_ws`)本身能正常工作，只是不打算用在避障这条路上。
- **定位：只是备用方向，采不采用要看后续有没有数据支撑**——2D雷达只有水平面信息没有高度，查资料显示"融合雷达+视觉+惯导优于单独雷达里程计"，没有证据支持2D雷达能独立替代视觉惯导定位。目前T265没有暴露出定位精度不够的证据(已知问题是冷启动检测/安装角度，不是精度问题)，跟当年[[project已知问题3]](T265+光流融合)的决策逻辑一致：没有实测证据支撑必要性，优先级排后面，等以后真的观察到具体的定位不够用场景再重新评估。

**2026-07-08 已修复：`PoleTracker`改成世界系位置聚类匹配，并接入`Mission_GPT.py`导航流程**——`update()`把候选点转换到世界系坐标(新增`body_to_world_xy()`)再存历史，`confirmed_poles()`按世界系距离分组(取代机体系角度/距离容差)，静止杆子不管飞机怎么移动/转向都能被稳定匹配。**验证方式**：07-07真机测试没记录雷达点云到飞行日志，只能用真实T265轨迹+按台架命中率合成候选点回放对比(`drone_control/tools/replay_pole_tracker.py`)——第一次直接用日志~65ms采样喂算法测不出问题(6帧窗口覆盖时间太短，方位角来不及摆动)，改成按真实0.5s轮询间隔重采样后，5个随机种子测试显示新版全程保持确认(0次丢失)、旧版在摆动阶段反复丢失确认(最差种子连续9帧)。**已接入导航**（仅`basic_radar/`，`Mission_GPT.py`的`navigate()`）：`DRONE_RADAR_ENABLED=1`才启用，检测到确认杆子距当前位置<0.6m就悬停，不绕行；真实障碍物悬停后不会自动恢复(需人工接管)，只有误报才自动恢复。**`yaw_sign`(世界系旋转符号)依然未标定**——回放验证用同一假设值生成数据和跑算法，天然自洽，证明不了符号对不对，这个值现在直接决定悬停判断的世界坐标准不准，下次真机操作应优先标定(参照`debug_coordinate.py`当年标定T265坐标系的方法)。

**2026-07-08 台架手持转动标定yaw_sign失败，已放弃这种方式**：新增`calibrate_yaw_sign.py`(雷达+T265刚性固定，实时对比sign=+1/-1算出的世界坐标)，台架手持转动两轮测试结果互相矛盾——转到约90°时sign=-1更接近不变(漂移0.79m vs sign=+1的1.51m)，但再转到约135°时反过来了(sign=+1漂移1.54m反而比sign=-1的1.62m略小)，判断不出稳定规律。**根因推测**：手持转动的转轴不经过雷达/T265光心，转动本身引入"假"平移分量，跟符号误差混在一起分不清，加上细杆子本身命中角度就有几度抖动(混合像素效应)，大转角下被放大。**结论：台架手持转动这种标定方式不可靠，已放弃**，留到真机飞行时用无人机自身yaw转动标定(更精确，没有转轴偏移问题)。**顺带发现**：雷达实际串口是`/dev/ttyACM0`，不是脚本默认的`/dev/ttyUSB0`(USB枚举顺序不保证稳定)，连接前建议先`lsusb`/`ls /dev/serial/by-id/`确认实际端口。

**2026-07-08 决定：yaw_sign真机标定优先级降低，暂不专门测**——`navigate()`把yaw_pid目标固定设成0，实际飞行yaw基本贴着0°(问题11观测到真实漂移只2-5°)，`body_to_world_xy()`在yaw=0时两个符号结果完全相同，只有yaw明显偏离0才有实质差异，5°量级误差换算到1m探测距离只有几厘米，跟已知15cm悬停噪声(问题8)同一量级，收益不高，暂不安排真机旋转测试。跟T265+光流融合决策(项目已知问题3)"没有实测证据支撑必要性，优先级排后面"同一逻辑。

**2026-07-14 新发现：飞行振动会导致雷达USB连接物理断开，进而级联到飞控串口超时紧急降落**——circle_pole阶段2视觉伺服真机测试(APPROACHING纯视觉触发验证)时，起飞后约35秒`dmesg`记录雷达USB转串口芯片(1a86:55d4)物理断开又重新枚举(device number 8→10)，`/dev/radar`软链接从指向`ttyACM0`变成`ttyACM1`；雷达后台监听线程(`Lradar.py:_listen_loop`)因此抛`SerialException: device reports readiness to read but returned no data (device disconnected or multiple access on port?)`崩溃，2秒后飞控串口也超时，触发`Mission_GPT.py`现有的"飞控串口超时2s紧急降落"安全机制(这个安全机制本身工作正常，是它救的场)。**跟本session更早时候静态测试摆放摄像头时"换USB口顶掉雷达连接"是同一类问题的另一种触发方式**——之前是插拔导致，这次是飞行振动导致，说明雷达/USB硬件走线本身不够牢靠，不是一次性巧合。**How to apply**：以后凡是真机测试(尤其带雷达)之前，除了软件层面的udev固定命名，还要现场检查/加固雷达USB线缆的物理牢靠程度(比如加装扎带固定、检查接口是否有松动)；如果以后又遇到"雷达线程崩溃+飞控串口超时紧急降落"的组合症状，先查`dmesg`看有没有对应时间点的USB disconnect/reconnect记录，不要默认当成新的软件bug排查。
