多版本（`basic`/`basic_radar`/`original`）都要改的代码变更，不要一次性把所有版本都同步到板子。先只同步当次真机测试实际会用到的那个版本，跑通真机验证之后，再把改动同步到其他版本。

**Why**：如果改动本身有问题（比如逻辑错误、真机测试暴露新bug），只有一个版本被污染，其余版本保持在已知良好状态，不会一次性把所有版本都置于未验证状态。用户在完成到达确认滑动窗口重构后明确提出这个顺序要求。

**How to apply**：
- 判断当次会话接下来要用哪个版本做真机测试（通常是 `basic_radar`，因为它是当前主要测试对象）。
- 先只 scp 同步该版本到 pi、跑单元测试、（如果当次会话继续做真机飞行）等真机验证通过。
- 其他版本（`basic`/`original`）的相同改动可以先在本机改完、本机测试通过，但先不要 scp 到板子；等目标版本真机验证通过后再补同步。
- 如果当次会话不会立即做真机测试（纯代码修复，不安排飞行），三个版本可以一起同步，这条约定主要针对"改动+马上要真机验证"这种场景。
