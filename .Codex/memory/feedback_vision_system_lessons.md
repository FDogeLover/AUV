2026-07-23，基于 circle_pole / fire_patrol / warehouse_inventory 三个版本的视觉系统调试经验归纳。

## 已确认的实测结论

**板载视觉伺服在三个版本里均因频率不足关闭**
circle_pole（APPROACHING横向PID）、fire_patrol（APPROACH固定增益步进）、warehouse_inventory（视觉伺服X/Z对中）都最终关闭了视觉伺服功能，根因相同：板载端同时承担T265/飞控通信/雷达/状态机后，剩余计算资源不足以维持视觉处理的端到端刷新频率。视觉线程结构本身没错（后台采集+latest()共享），但板子的调度能力是硬约束。

**QR解码：高频原图优于低频后处理（warehouse_inventory 实测）**
CLAHE/透视校正/自适应阈值/多尺度变体等后处理叠加后帧率下降，单位时间内送给解码器的帧数减少，解码成功率反而更低。ZBar/pyzbar等解码库内部已针对原始图像优化（内置灰度化和局部自适应二值化），外加的预处理相当于重复处理，且可能引入失真。结论：先测原图基准帧率和成功率，只在数据证明有用时才加预处理。

## 可推广的工程原则

**标定距离必须等于实际工作距离**
同一颗摄像头同一根杆子，~5m距离标定绿色饱和度S中位14~24，~2m距离标定时S集中26~89——相差3倍以上。在方便的地方标定，在实际距离用，等于用错误阈值飞行。此原则同样适用于焦距标定、QR解码距离、激光高度反光等所有距离依赖的参数。

**单特征过滤遇到同色竞争目标必须引入第二特征**
天花板横梁与绿色杆子HSV重叠，调阈值无法区分。解决方法：加高宽比≥1.2（来自对象真实几何形状，非数据拟合）。通用原则：目标所在环境中存在同色物体时，纯颜色过滤不稳定，必须引入至少一个与颜色独立的几何或结构特征。写需求时必须描述"场景中可能有哪些同色干扰物"。

**控制律符号错误的诊断方法**
POLE_VISION_Y_SIGN 曾误诊为雷达坐标异常，实因发散被雷达快速接管侥幸掩盖。正确诊断流程：
1. 理论推导：target=0时，error = 0 - azimuth × sign，推出符号关系
2. 对照飞行日志逐样本核对输出与误差的符号关系
3. 全部样本同向 → 正反馈，符号写反；全部反向 → 负反馈，符号正确
不要先调增益或换其他参数，先做符号推导，再用日志验证。

**分辨率与焦距隐式耦合是常见无声错误**
CAMERA_FOCAL_PX=1100 按 1920宽度标定，摄像头默认给出 320×240 帧，azimuth_from_dx() 拿小尺度 dx_px 除以大焦距，方位角完全错误但不报任何错误，只有飞行轨迹偏才发现。给 AI 写视觉需求时，分辨率和焦距必须作为显式约束捆绑，不能只说"用焦距换算方位角"而不注明分辨率假设。

**同一架构假设被三个版本重新发现**
三个版本均未提前做计算资源预算，而是飞行测试后才发现板载视觉伺服不可行。正确顺序：
1. 测飞控基线 CPU 占用（T265 + 串口 + PID + 状态机）
2. 测目标视觉处理在目标帧率下的 CPU 占用
3. 确认两者加起来 < 可用预算（留足调度余量）
4. 预算不够时先决定架构（板端/离板/降帧），再写代码

**调试图像接口应在设计阶段就规划**
pole_vision 的 DRONE_VISION_DEBUG_DIR 和 DX_JUMP_DEBUG_THRESHOLD_PX 都是真机出问题后追加的。实用规则：任何向飞控提供连续输入的视觉模块，设计时就应预留：
- 每次检测结果的时间戳和帧序号
- 原图 + 掩码 + 检测结果叠加图的可选保存
- 异常帧（跳变/低置信度/无检测）的自动存档触发条件
- 不依赖飞行的离线重放接口（输入一张图，输出检测结果）

## 向 AI 表达视觉模块需求的补充约束

写视觉模块需求时，除了通用约束模板外，必须额外说明：
```
帧率约束：目标最低帧率 X fps，每帧处理预算 Y ms（按板子可用CPU余量估算）
标定条件：在什么距离/环境下标定的，什么条件下参数会失效
干扰物描述：场景中存在哪些可能被误识别的同色/同形物体
失效行为：视觉丢失/数据过期时飞行器的允许行为和禁止行为
调试接口：离线重放接口是否必须，调试帧保存的触发条件
```
