# 绕障飞行器（D题）阶段2 — 前置摄像头颜色识别 + 视觉伺服接近 设计

日期：2026-07-14
前置文档：`docs/superpowers/specs/2026-07-13-circle-pole-design.md`（阶段1设计+真机验证结果+阶段2早期视觉辅助讨论，本文档是对其中"阶段2视觉辅助方案"一节的落地设计，部分早期结论已被推翻，见下方"与前置文档的差异"）

## 背景

阶段1（单杆环绕）已真机验证通过。阶段2要处理双杆场景：赛题要求红/绿两根杆塔分别顺时针/逆时针环绕，此前设计一直搁置颜色识别（环绕方向固定顺时针）。本次把颜色识别和视觉辅助接近一起做，同时解决方向判断和阶段1遗留的"已环绕杆塔漂移误判成新杆塔"已知限制。

## 与前置文档的差异

`2026-07-13-circle-pole-design.md`早期讨论认为颜色识别搁置、视觉只在"环绕前"做一次性对准。本次讨论范围扩大：
- **颜色识别不再搁置**：直接决定环绕方向（红=cw/绿=ccw），顺带提供比坐标容差更可靠的"是否已环绕过"判断依据
- **视觉不是一次性对准，而是贯穿整个接近过程的闭环控制**：新增独立状态`APPROACHING`，接近阶段完全由"视觉定y+雷达定x"接管，不依赖`patrol_router.txt`航点
- **降落路径改为可配置航点文件**，不再是硬编码单点常量

## 状态机

```
PATROL → APPROACHING → CIRCLING → (退回基准线) → PATROL / TO_LANDING → LANDING
```

### PATROL（巡航搜索）
- 沿`patrol_router.txt`（原`router.txt`改名，横向搜索杆塔用，用户提供）飞行，`navigate()`逐点飞完，到达确认机制不变
- 雷达`PoleTracker`按`POLE_POLL_INTERVAL_S`(0.5s)轮询，持续尝试确认杆塔世界坐标
- 前置摄像头后台线程持续拉帧做红/绿HSV检测，主循环每次只读线程共享的最新结果（`dx_px`/颜色/时间戳），不阻塞30ms主循环
- 现有悬停避让机制不变：雷达确认的、还没开始处理的杆塔进入`POLE_DANGER_DIST_M`(0.75m)内照常触发悬停
- **触发条件（PATROL→APPROACHING）**：雷达确认出一个杆塔 **且** 该杆塔当前雷达世界坐标对应的方向上，视觉同一时刻也看到了红/绿目标 **且** 该颜色不在`circled_colors`集合中（已绕过的颜色不会再触发，见下方"去重机制"）。三者同时满足才触发。
- **触发滞回（2026-07-14新增）**：三个条件不能只看单次瞬时读数——雷达确认本身有轮询延迟(0.5s)，视觉色块检测在边界距离/轻微遮挡下容易抖动，单帧满足就触发容易在边界条件反复触发/撤销。参考现有`ARRIVAL_CONFIRM_RATIO`滑动窗口思路，改成在一个短时间窗口内（如最近1秒的轮询/检测帧）多数帧同时满足三个条件才真正触发，避免PATROL/APPROACHING抖动切换、原地打转浪费时间（5分钟总时限下抖动是实质代价，不只是体验问题）
- 触发时：保存当前`target_index`（用于APPROACHING/CIRCLING结束后恢复），记录目标杆塔的雷达世界坐标+颜色，切换到`APPROACHING`

### APPROACHING（视觉接近）
不再跑`patrol_router.txt`航点，改为无航点的主动控制：
- **x方向（前进）**：固定两档速度——雷达距离>0.8m用较快巡航速度，≤0.8m降为较慢微调速度，朝杆塔靠近。不做比例控制，两档阶跃即可。
- **y方向（横向对准）**：完全交给视觉伺服，不参考`navigate()`的y_pid。方位角`atan(dx_px/1100)`（dx_px=检测到的目标像素x - 画面中心960，1100px为已标定焦距）作为PID误差量，目标设0（居中），每次新一帧结果更新一次，持续输出y方向速度指令
- **颜色锁定（2026-07-14新增）**：APPROACHING期间画面里可能同时出现两根杆塔的色块（比如接近红杆时绿杆恰好从旁边入镜）。视觉检测不能是"每帧挑最大色块"——如果另一色的色块面积恰好更大，`color`字段可能中途从锁定颜色跳到另一色，y轴伺服会瞬间对齐错误目标，方向判断也会跟着乱。**修复**：进入APPROACHING时锁定当次颜色，之后整个APPROACHING阶段视觉检测只匹配锁定颜色对应的HSV范围，忽略另一色的色块（即使它更大/更明显）
- **悬停避让**：当前目标杆塔从悬停避让判断中临时排除（复用`_exclude_circle_target`思路，容差沿用`POLE_CIRCLE_RADIUS_M+POLE_CIRCLE_EXCLUDE_MARGIN_M`），其余未确认/未处理的杆塔仍正常触发悬停避让（阶段2双杆场景的安全网，APPROACHING阶段离另一根杆通常还有整个杆间距的余量，不像CIRCLING那样天然贴近悬停阈值，见下方CIRCLING一节的对比）
- **目标丢失判定**：视觉结果超过0.5s未更新（含摄像头/线程故障导致的结果陈旧）视为目标丢失。丢失时不做原地悬停等待，直接退回`PATROL`，恢复保存的`target_index`继续跑`patrol_router.txt`；下次雷达+视觉+去重条件再次同时满足会重新进入`APPROACHING`
- **触发条件（APPROACHING→CIRCLING）**：雷达距离降到`POLE_CIRCLE_RADIUS_M`(0.7m)。环绕方向由本次进入APPROACHING时记录的颜色决定（红=cw/绿=ccw）

### CIRCLING（环绕）
- 复用现有`circle_planner.generate_circle_waypoints()`生成7个环绕航点（含闭合点），`navigate()`逐点飞完（到达确认机制不变）
- **CIRCLING阶段悬停避让整体关闭（2026-07-14修正，替代阶段1"只排除当前环绕目标、其余正常避让"的表述）**：赛题只保证杆塔间距≥150cm，环绕半径`POLE_CIRCLE_RADIUS_M`=0.7m时，环绕到最靠近另一根杆的那个点，最坏情况距离=150-70=80cm，只比悬停触发阈值`POLE_DANGER_DIST_M`(0.75m)高5cm——这个理论安全边际被已知的定位噪声(`confirmed_poles()`世界坐标估计漂移0.4~1m量级、悬停位置漂移~15cm)完全吞掉，实测大概率会被另一根杆子的悬停判断中途打断。而环绕过程本身是近距离转弯的主动机动，中途被悬停打断风险比"环绕时忽略其他杆子"更高（可能带残余转弯惯性直接怼向目标杆）。**决定**：`navigate()`中`nav_mode=="CIRCLING"`时完全跳过悬停避让检查（`pole_hover`恒为`False`），不只是排除当前目标；代价是两杆间距贴近150cm下限时，环绕过程中确实可能物理上更接近未处理的第二根杆，但这是赛题固有空间约束，只能靠信任环绕路径规划本身、不做实时避障来处理。PATROL/APPROACHING阶段不受影响，仍用现有悬停避让+`_exclude_circle_target`排除机制
- 环绕完成：该杆塔的`(x, y, color)`加入`circled_poles`列表（**坐标继续保留用于绕行安全区检查，不因去重机制改动而移除**），对应颜色加入`circled_colors`集合
- 已环绕过的杆塔从悬停避让永久排除、直飞路径穿越安全区时插绕行航点——这两处阶段1机制不变（绕行机制发生在PATROL/TO_LANDING态，不受本次CIRCLING悬停关闭的影响）
- 先用`navigate()`飞到`(x=0, y=当前y位置)`退回基准线，到达后：
  - 若`circled_colors`集合还不满2个 → 恢复保存的`target_index`，回到`PATROL`继续找下一根
  - 若`circled_colors`集合已满2个（红绿都绕完）→ 切换`TO_LANDING`

### TO_LANDING（返航降落）
- 加载`landing_router.txt`（两根杆子都绕完后的返航路径，用户提供），`navigate()`逐点飞完
- 走完最后一个航点 → 转`LANDING`（复用现有`navigate()`通用逻辑：`nav_mode=="TO_LANDING"`且航点耗尽即转`LAND`，不用改代码）

### LANDING（降落）
调用现有`land()`，不改动。

## 去重机制：颜色代替坐标容差

阶段1已知限制记录过：`_already_circled()`用1.1m经验容差判断"是否已环绕过"，如果杆塔坐标估计漂移超过1.1m会被误判成新杆塔，阶段2场景下可能导致提前判定"两根都绕完"从而漏掉真正的第二根。

**本次设计用颜色集合彻底替代这个坐标容差判断**：
- 维护`circled_colors`（最多2个元素的集合：`{"red"}` / `{"green"}` / `{"red","green"}`）
- `PATROL→APPROACHING`触发前检查目标颜色是否已在`circled_colors`中，在了就跳过，不触发
- 颜色是硬边界（只有红/绿两种），不存在"漂移导致误判"的问题，比坐标容差可靠得多
- `circled_poles`的坐标数据继续保留，但只用于绕行安全区检查（`_maybe_insert_detour`），不再参与"是否已环绕过"的判断

**新引入的风险：颜色误分类不可逆（2026-07-14审查发现）**：坐标容差的问题是"漂移导致同一根杆被误判成新杆"，颜色去重把这个风险换成了"单帧颜色误判导致错误颜色被永久记入`circled_colors`"——如果APPROACHING触发那一刻背光/曝光问题导致红杆被识别成绿（或反之），这根杆会被当成"绿色"整圈绕完并写入`circled_colors`，之后真正的绿杆再也不会被触发（集合判断"已经绕过"），且没有回退机制。**缓解**：APPROACHING触发前颜色判断需要连续多帧（如5帧）一致才锁定，不能是单帧快照决定，降低瞬时误判被写入永久状态的概率（不能完全消除，只是降低概率）。

## 视觉子系统

- 硬件：前置1080p USB摄像头，`/dev/video0`，MJPG格式，自带ISP，标准UVC协议
- 已标定参数（`drone_control/tools/camera_test_20260713/`）：水平FOV≈82°，焦距≈1100px@1920宽
- **独立后台线程**持续`cv2.VideoCapture.read()`拉帧+HSV阈值分割找红/绿最大连通域，主循环每tick只读线程共享的最新检测结果（`dx_px`/颜色/时间戳），不阻塞30ms主循环通信实时性（与现有`listen_fc()`后台线程风格一致）
- HSV阈值需现场标定（红色注意色相环绕0°/180°两段，OpenCV需要两段`inRange`取并集），代码里先给经验初始值，真机测试时调整
- 检测输出：`{dx_px, color, timestamp}`，`color`取值`"red"`/`"green"`/`None`（无目标）

## 航点文件

- `patrol_router.txt`：巡航搜索杆塔用（原`router.txt`改名），格式不变（`x,y,z`逐行）
- `landing_router.txt`：两根杆塔都绕完后的返航降落路径，格式与`patrol_router.txt`一致，用户提供
- 两个文件都需要用户在真机测试前实测现场量出

## 测试计划

- 单元测试：HSV检测函数（给定合成图像验证`dx_px`/颜色输出）、方位角换算公式、`circled_colors`去重逻辑（同色第二次不触发APPROACHING）、颜色锁定逻辑（锁定后忽略另一色更大的色块）、CIRCLING阶段悬停避让确实被跳过（`pole_hover`恒为False）
- 台架测试：拆桨通电，验证后台视觉线程不阻塞主循环通信（观察帧1到达率仍维持~50Hz）、HSV阈值在现场光照下的识别稳定性、双色同时摆在镜头前验证颜色锁定不会中途切换目标

**真机测试严格按模块顺序推进，每一部分独立验证通过后才进入下一部分，不跳步直接测整体链路（2026-07-14确定）**：

1. **原地悬停 + 颜色识别**：飞机原地悬停（或干脆先拆桨台架，视HSV调参需要几次迭代而定），杆塔摆在视野不同位置/距离，验证红/绿颜色分类准确率、`dx_px`计算是否符合预期、颜色锁定多帧防抖是否生效，重点调HSV阈值到现场光照下稳定
2. **PATROL巡航中的检测效果**：沿`patrol_router.txt`正常巡航，不触发APPROACHING（或先屏蔽触发逻辑），只观察移动中颜色识别的稳定性（运动模糊、光线变化、色块时有时无导致的检测抖动），确认第1步调好的HSV阈值在真实巡航速度下仍然可用，需要的话回头再调
3. **APPROACHING单独验证**：允许触发APPROACHING，但先不接入CIRCLING（比如到达触发距离后直接悬停/回PATROL，不真的开始环绕），验证x两档限速接近、y视觉伺服居中、颜色锁定不被另一色打断、目标丢失0.5s超时正确退回PATROL并恢复`target_index`
4. **APPROACHING→CIRCLING衔接**：接入环绕，单杆验证完整`APPROACHING→CIRCLING`链路（复用阶段1单杆环绕已验证过的`CIRCLING`本身，重点验证这次新增的触发衔接和颜色→方向映射是否正确）
5. **双杆整体链路**：单杆各部分都验证通过后，才测双杆完整流程——颜色去重、连续两次`APPROACHING→CIRCLING`、退回基准线、`TO_LANDING`返航，双杆间距刻意贴近150cm下限专门测试CIRCLING阶段是否会被另一根杆异常打断

## 已知限制（记录，非本次要解决）

- HSV阈值受现场光照影响，室内外/不同灯光条件下可能需要重新标定，暂无自适应白平衡/自动阈值机制
- APPROACHING阶段x方向固定两档速度是简化方案，非最优路径（比例控制更平滑但增加调参复杂度），当前判断收益不足以抵消复杂度
- 视觉后台线程与雷达轮询（0.5s周期）频率不同步，两者各自独立更新，`APPROACHING`触发条件"同一时刻都满足"实际是"两者最新读数都满足"，不是严格同一时刻的快照

## 2026-07-14审查：与赛题硬指标的两处已知偏差（比赛前必须复核，不属于本次实现范围）

- **环绕净空不达标**：赛题要求环绕距离50±10cm（净空40~60cm）。当前`POLE_CIRCLE_RADIUS_M=0.7m`是中心到中心距离，`Mission_GPT.py`注释里反推的机身等效半径约0.4m，实际净空只有约30cm，明显低于要求下限。这个值是阶段1为测试安全和空间折中出来的，不是刻意瞄准50cm算出来的。本次设计把APPROACHING→CIRCLING的触发距离也直接沿用了这个0.7m。**待办**：阶段2真机链路跑通后，需要专项测试把半径上调到净空40~50cm量级（约0.8~0.9m中心距），不能带着阶段1的折中值进比赛。
- **巡航高度不达标**：赛题要求150±10cm，当前`patrol_router.txt`全程`z=1.2m`，是阶段1网兜测试空间的高度限制，两份设计文档都没有明确标注"这是暂定测试值"。**待办**：比赛前必须把航点高度改到140~160cm区间，并重新验证到达确认、环绕半径等所有跟高度耦合的参数在新高度下依然有效（更高的巡航高度可能改变雷达探测/悬停避让的实际表现，不能假设直接照搬阶段1参数没问题）。
