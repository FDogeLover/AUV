## 一、赛题完备分析（解答你关于"分析更完备"的思考）

### 1.1 显性要求提取
| # | 要求 | 关键指标 |
|---|------|---------|
| B1 | 从"十"字垂直起飞到150±10cm | 定高精度 |
| B2 | 找到起点A(区块21)开始撒药 | 视觉定位起点 |
| B3 | 360s内全覆盖绿色区块 | 路径效率+时间约束 |
| B4 | 降回"十"字偏差≤±10cm | 降落精度 |
| F1 | 3-4个连续块变灰 → 重新跑B1-B3 | 动态避障 |
| F2 | 识别杆塔条形码 → LED闪烁显示数字 | 视觉识别+GPIO |
| F3 | 在 数字×10cm 半径圆周上降落，偏差≤±10cm | 圆周降落算法 |
| F4 | **30分钟现场编程完成一个随机任务** | 开发效率 |

### 1.2 隐性约束（容易遗漏的点）
- **颜色容差**：题目注明"考虑材料及颜料导致颜色存在差异"→ HSV阈值不能硬编码，须可现场标定
- **场地光照**：室内灯光 vs 自然光对颜色检测影响巨大，必须有预处理
- **激光笔可见性**：地面环境光可能淹没激光光点，闪烁频率须可调
- **条形码方向**：环形条码，无人机视角从上方看，解码算法要适应旋转不变性
- **起飞漂移**：T265 起飞瞬间的漂移可能导致起点偏移→需在NAVIGATE到区块21之前做位置校准
- **计时起点**：起飞开始计时至降落完成，360s含撒药时间（每块1-3次闪烁，1-2s周期→每块约3s）

### 1.4 风险预判（每个模块的"如果…怎么办"）
| 风险 | 概率 | 影响 | 预案 |
|------|------|------|------|
| 颜色检测不稳定（光照变化） | 高 | 高 | HSV阈值现场标定 + 用区块编号映射回退（不依赖视觉仍可覆盖） |
| 条形码在小分辨率下不可读 | 中 | 中 | 悬停在杆塔正上方→拍照→放大解码，不要求飞行中识别 |

| 实机首飞就炸 | 低 | 高 | 首飞先跑空航线（不撒药），确认路径正确再开激光 |

### Phase 1：网格坐标 + 全覆盖路径（纯逻辑，不上板）

**模块**：
- `Lcode/field_map.py` — 场地坐标系定义，1-28号格→xy坐标，起点A定位
- `Lcode/coverage_path.py` — S型全覆盖路径生成器（按行扫描），支持动态跳过指定块
- `test_field_map.py` + `test_coverage_path.py`

**测试策略**：⭐ **充分测试，不上板**

| 测试项 | 方法 | 耗时 |
|--------|------|------|
| 网格坐标映射（全部28个格+起点A） | pytest 参数化 @pytest.mark.parametrize | <1s |
| S型路径覆盖所有绿块 | 生成路径→验证覆盖无遗漏无重复 | <1s |
| 跳过指定块（模拟F1场景） | 标记3-4块为灰色→验证路径跳过 | <1s |
| 路径总耗时估计（360s内） | 路径长度/巡航速度→估计耗时 | <1s |
| 边界条件（全部灰块、全部绿块） | 极端输入测试 | <1s |

**提速要点**：所有测试都是纯Python数学计算，不涉及任何硬件，可以本地 `pytest -x -q` 秒级跑完。这部分应该**写最全的测试**，因为迭代成本几乎为零。

### Phase 2：核心飞行任务（板上模拟 → 实机首飞）

**模块**：
- `plant_mission.py` — 植保任务状态机（继承 basic 的 Mission_GPT）
  - 新增 `COVER` 状态：驱动覆盖率路径，到点触发激光闪烁，完成后转 `RETURN`
  - `TAKEOFF` → 150cm 定高（复用 basic）
  - `NAVIGATE` → 飞到起点 A（复用 basic 导航）
  - `COVER` → 遍历覆盖路径各点
  - `RETURN` → 回到"十"字上方
  - `DESCEND` + `LAND`（复用 basic 两级降落）
- `Lcode/laser_spray.py` — 激光笔闪烁控制（基于 gpio_led.py 的闪烁模式）

**测试策略**：⭐ **最小的板上 smoke test → 直接实机**

| 步骤 | 方法 | 目的 | 耗时 |
|------|------|------|------|
| ① 本地pytest Mission_GPT逻辑 | mock 硬件，验证状态转换 | 秒杀纯逻辑bug | <10s |
| ② 板上硬件预检 | `python hardware_preflight.py` | 确认串口/GPIO正常 | 30s |
| ③ 板上dry-run航线 | `--dry-plan` 打印航点 | 确认航线坐标正确 | 10s |
| ④ **实机第一架次（不撒药）** | 飞覆盖路径但不闪激光 | 验证路径、高度、降落 | 5min |
| ⑤ 看日志调参 | 分析飞行日志 | 微调速度/确认时间 | 5min |
| ⑥ **实机第二架次（全功能）** | 开激光撒药 | 完成B1-B4 | 5min |

**提速要点**：
- **不做复杂的板上模拟**：不在板上 mock 摄像头、mock 颜色识别来跑全集成测试。只需要确认硬件通路正常、航线坐标正确就行
- **首飞不撒药**：先确认飞机不会炸，再开功能
- 所有 m/s 级的参数（巡航速度、悬停确认时间、闪烁次数）在 **实机之间用日志分析调**，不上板反复跑

### Phase 3：视觉颜色检测（离线验证 → 实机）

**模块**：
- `Lcode/color_vision.py` — 基于 VideoSource + OpenCV 的颜色检测
  - HSV 阈值可配置（现场标定用）
  - 绿/灰二分类 + 黑色边界线检测
- `Lcode/field_observer.py` — "当前在哪个区块"的视觉估测
  - 结合 T265 位置 + 颜色确认，判断当前所在网格

**测试策略**：⭐ **用录制素材离线验证，减少实机调试次数**

| 步骤 | 方法 | 耗时 |
|------|------|------|
| ① 拍摄一组场地照片/视频（不同光照） | 用摄像头录5-10秒 | 赛前一次 |
| ② 离线 python 回放 → 调HSV阈值 | 视频回放 + 可视化mask | <5分钟 |
| ③ pytest 颜色分类（用录制数据） | fixture 加载录制帧，验证绿/灰分类 | <1s |
| ④ 机上 dry-run（开视觉但不飞） | 板上跑视觉模块，看识别输出 | 2分钟 |
| ⑤ **实机第三架次（+视觉避障）** | 动态跳过灰色块 | 5min |
| ⑥ 日志对比 | 对比视觉识别的块 vs 实际路径 | 3min |

**提速要点**：
- **颜色阈值调试在离线完成**，不在实机上反复起降调HSV值
- 实机前用一帧帧回放确认分类稳定性胜过任何单元测试
- 如果视觉不稳定 → 回退到"按预设编号飞"（不依赖视觉也能完成B3，只是不能处理F1）

### Phase 4：条形码 + 圆周降落（离线验证 → 实机）

**模块**：
- `Lcode/barcode_decoder.py` — 环形条码解码
  - 图像预处理 → 环状区域检测 → 条码编码解码
  - 支持旋转不变性
- `Lcode/circle_landing.py` — 圆周降落控制器
  - 飞到圆周上任意点 → 沿圆周移到目标扇区 → 降落

**测试策略**：⭐ **条码解码离线充分验证，圆周降落直接实机**

| 步骤 | 方法 | 耗时 |
|------|------|------|
| ① 生成不同数字的模拟条码图片 | Python 生成测试数据 | 赛前一次 |
| ② 离线pytest解码器 | 覆盖所有数字+不同角度旋转 | <1s |
| ③ 打印真实条码+摄像头拍照验证 | 真实硬件测试解码 | 2分钟 |
| ④ 板上集成测试 | VideoSource 读取→解码→LED闪烁 | 2分钟 |
| ⑤ **实机第四架次（条形码识别）** | 飞到杆塔上方，识别→LED显示 | 5min |
| ⑥ **实机第五架次（圆周降落）** | 完成F3 | 5min |

**提速要点**：
- 条码解码器的测试**不需要无人机**，一个USB摄像头+打印的条码就够了
- 圆周降落算法可以先在无风环境下用"飞到圆周上某个偏移点→lock→降落"的简化方案
- 如果圆周降落不稳定 → 回退到"降回原'十'字"（B4已满足基础分，圆周是发挥项）

## 四、你的两个核心问题的总结回答

### 问题1：分析题目如何更完备？
**三步拆解法**：
1. **显性→隐性**：把题目字面要求列完后，追问"还有什么没说但会出问题的？"（光照、漂移、容差、计时…）
2. **模块→依赖图**：画依赖树，找可以并行开发的无依赖模块（如FieldMap可以和状态机同时写）
3. **风险→预案**：每个技术点问"如果这个搞不定，备选方案是什么？"（如：视觉搞不定就按编号飞）

### 问题2：测试如何提速？
**核心原则：测试深度与风险成反比，与变更频率成正比。**

| 测试层级 | 适用场景 | 投入时间 | 作用 |
|---------|---------|---------|------|
| **纯逻辑测试**（本地pytest） | 路径规划、坐标变换、解码算法 | 充分（全覆盖） | 防回退，低代价捕捉bug |
| **硬件smoke test**（板上一次） | GPIO、串口通信、VideoSource初始化 | 最小（能通即可） | 确认硬件通路，不追求覆盖 |
| **集成模拟** | 状态机全流程、异常处理 | **跳过或极简** | 实机本身就是最好的集成测试 |
| **实机测试** | 验证最终效果 | 全力投入 | 一切以实机为准 |

**每轮迭代：本地改代码 → 本地pytest(纯逻辑) → SCP上板 → 板上smoke(仅硬依赖) → 实机**

**不要做**：用复杂的 mock 框架在本地模拟整个场地飞行环境——那比直接实机飞还慢，而且永远模拟不准。
