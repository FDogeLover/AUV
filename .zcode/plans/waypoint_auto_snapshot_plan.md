# 计划：航点自动截图消费者

## 问题描述 & 目标

当前备赛版本已经能够在飞行状态机确认航点到达后发布 `ACTION_REQUESTED` 事件，也预留了统一的 `VideoSource` 接口，但事件尚未驱动截图，截图结果也没有进入同一次 `scout/execute` 会话。

目标是在不阻塞 30 ms 飞控主循环、不改变解锁/导航/降落链路的前提下，增加硬件无关的航点截图消费者。无论后续采用 UVC 采集卡接收成品图传，还是采用开发板间 RTSP/RTP/UDP 网络视频，只要对应后端实现 `VideoSource`，截图消费者均不需要修改。默认保持关闭，未确定硬件时不连接摄像头、不影响现有飞行。

## 方案选择

| 方案 | 优点 | 缺点/风险 |
|------|------|----------|
| 方案A：在 `Mission_GPT.navigate()` 到达分支直接截图 | 实现简单，触发点直观 | 视频读取可能阻塞飞控循环；图传故障会污染安全关键路径；与飞控代码强耦合 |
| 方案B：事件总线消费者直接同步截图 | 不阻塞飞控线程，改动较小 | 单次截图会阻塞事件总线，导致会话记录和其他消费者延迟 |
| 方案C：独立的有界截图工作队列 | 飞控线程和事件总线都只做非阻塞入队；视频故障与飞行隔离；可统一兼容两种 `VideoSource` | 生命周期、队列溢出和结果回传逻辑更多，需要专门测试 |

**选择方案C。** 飞行安全优先于实现简洁；截图延迟、断流或解码失败不得占用飞控线程，也不得触发飞行紧急状态。独立有界队列还能避免视频后端卡顿导致无界内存增长。截图消费者按每次阶段运行创建，持有唯一 `run_id`，不跨进程重用。

## 改动范围

- `drone_control/competition_2026/Lcode/waypoint_snapshot.py` — 新增 `SnapshotPolicy` 与 `WaypointSnapshotConsumer`；仅消费指定动作的 `ACTION_REQUESTED`，在独立守护线程调用带超时契约的 `VideoSource.snapshot()`，发布 `SNAPSHOT_SAVED` 或 `SNAPSHOT_FAILED` 结果事件；采用有界队列、单次运行去重、连续失败熔断、截图数量上限并统计丢弃任务。
- `drone_control/competition_2026/Lcode/mission_events.py` — 增加截图成功/失败事件常量，沿用现有 `MissionEvent` 数据结构和非阻塞事件总线。
- `drone_control/competition_2026/Lcode/video_source.py` — 明确 `snapshot(timeout_s)` 的后端级超时、会话目录约束及同目录临时文件原子替换契约；不增加具体 UVC/网络流依赖。
- `drone_control/competition_2026/Lcode/mission_session.py` — 为每次 `scout/execute` 启动生成唯一 `run_id` 并写入计划/结果；无需引入视频依赖；继续通过已有事件记录器把截图结果写入独立追加式 `events.jsonl`，图片存入当前会话的 `snapshots/`。现有 `session.json` 继续使用临时文件原子替换，不与图片共用文件句柄。
- `drone_control/competition_2026/competition_main.py` — 读取自动截图策略；只有策略启用且活动图传配置存在时才创建并启动 `VideoSource` 和截图消费者；在飞行结束或异常退出时按“停止接收新任务 → 排空/停止消费者 → 释放视频源 → 关闭事件总线”的顺序回收资源。
- `drone_control/competition_2026/competition_config.json` — 增加默认关闭的 `auto_snapshot` 配置，包括触发动作、超时、队列长度和 `required` 开关。
- `drone_control/competition_2026/test_waypoint_snapshot.py` — 使用假视频源覆盖动作过滤、成功截图、失败结果、队列/停止行为，禁止测试依赖真实摄像头。
- `drone_control/competition_2026/test_video_source.py` 或入口测试 — 覆盖配置校验以及默认关闭时不创建视频后端。
- `drone_control/competition_2026/README.md` — 中文说明启用方式、两种图传共用接口、失败策略、会话截图位置和真机前检查项。

## 风险点

- 安全隐患：视频初始化、读取和保存均可能卡顿或抛异常。所有截图操作必须位于独立后台线程；飞控和事件总线只做 `put_nowait()`，不等待截图结果。运行中图传失败只记录 `SNAPSHOT_FAILED`，不得调用急停、降落或修改飞控指令。
- 启动策略：默认 `auto_snapshot.enabled=false`。启用后若后端不可用，`required=false` 时明确报警并继续飞行，`required=true` 时必须在进入一键起飞按钮和飞控串口初始化之前终止任务。
- 边界条件：同一点位可能因定位抖动重复产生事件；使用“本次阶段运行的 `run_id` + 航点索引”作为去重键。每次阶段启动创建新消费者和新 `run_id`，进程重启或重新执行阶段不会继承旧缓存；重复的 `HOME` 使用不同索引区分。T265 短暂重捕不会改变当前航点索引。
- 超时与底层阻塞：`VideoSource.snapshot(timeout_s)` 的具体后端必须把超时传入 V4L2/GStreamer/FFmpeg/网络读取层，而不是仅在 Python 外层计时。若后端违反契约永久卡住，最多占住唯一的截图守护线程；事件总线和飞控不等待它，队列保持有界且不再创建额外截图线程。这里不采用 `ThreadPoolExecutor.result(timeout)`，因为它无法终止已经卡死的底层线程，只会掩盖泄漏。消费者会在可检测的超时/连续失败达到阈值后熔断本次运行的视频源，不再接受截图任务。
- 队列与容量：队列满时不阻塞事件分发，丢弃新的截图请求并发布失败事件；配置单次运行最大截图数，达到上限后拒绝新任务，避免存储耗尽；会话结果记录接受、成功、失败、丢弃和熔断数量。
- 文件安全：点位编号先清洗为安全文件名，保存位置解析后必须仍位于当前会话 `snapshots/` 内。`VideoSource.snapshot()` 后端契约要求先写同目录 `.tmp` 文件、完成编码和 flush 后再原子替换为最终图片；异常只遗留可清理的 `.tmp`，不会产生被误判为成功的半张图片。
- 会话与日志隔离：截图消费者不写 `session.json` 和 `flight_data.jsonl`，只通过事件总线返回结果；会话元数据继续使用现有 `.tmp` + 原子替换。强制断电最多丢失末尾截图或 `events.jsonl` 最后一行，不会截断已完成的会话元数据或飞行日志。
- 关机边界：正常结束按“停止接收 → 有限等待消费者 → `VideoSource.stop()` → 关闭事件总线”回收；紧急停止或键盘中断最多等待配置的短超时。截图线程为守护线程且不持有飞控串口、GPIO、T265或飞控日志句柄，不能延迟紧急降落和主进程退出。
- 失败降级：连续失败达到阈值后熔断视频源并发布一次明确事件，不再反复读取；由于图传不是飞行安全传感器，熔断不得触发飞行状态变化。是否因失去图像而放弃计分任务由后续地面决策模块处理，不在飞控线程自动改变航线。
- 兼容性：当前 `capture_device` 和 `board_network` 只是已预留、尚未注册的后端。自动截图消费者完成后仍不会凭空获得真实画面；需要后续针对选定硬件实现对应后端。
- 回退方案：保持 `auto_snapshot.enabled=false` 即完全回到现有事件/会话行为；新增消费者不修改 `basic` 目录、不修改飞控协议，也不改变 `Mission_GPT` 的导航与降落判定。

## 验证方式

- 单元测试：用内存假视频源验证开始、截图、失败、停止、事件回传、动作过滤、同一 `run_id` 去重、新 `run_id` 可重新截图、连续失败熔断、最大截图数、队列溢出和无活动图传配置；验证截图消费者不触碰飞控日志及会话元数据；运行全部现有 pytest，确保飞控相关回归测试不变。
- 桌面测试：先运行 `--dry-plan` 验证默认配置不加载视频；再用假后端/本地测试后端模拟 `ACTION_REQUESTED`，确认图片路径和 `events.jsonl` 位于同一会话目录，且截图超时不会阻塞事件发布。
- 真机验证：第一阶段只在桨叶拆除状态下启用后端，验证断流、拔线和写盘失败；第二阶段低高度系留或安全网内飞行，验证到点时截图且飞控周期、急停和降落不受影响；正式飞行前再根据最终硬件实现 UVC 或网络视频后端并执行专门的上板检查。

## 第一轮 Qoder 高风险处理（用户选择 A）

1. **守护线程与文件损坏：** 截图与 `session.json`、`flight_data.jsonl` 完全隔离；会话元数据维持原子替换，图片后端采用同目录临时文件原子替换。守护线程不持有任何飞控资源，退出等待有上限。
2. **底层视频调用永久阻塞：** 明确后端级超时契约；单一截图守护线程即使卡住也不会阻塞飞控或事件总线，且不会继续派生线程。拒绝使用无法杀死底层卡死线程的伪超时方案；可检测失败达到阈值后熔断。
3. **去重生命周期漂移：** 每次 `scout/execute` 运行生成唯一 `run_id` 并创建新消费者，去重只在该消费者内生效；重启和重新执行不会继承缓存，T265 重捕不改变航点索引。
4. **中低风险补充：** 增加连续失败熔断、最大截图数、旧配置默认关闭回退，并明确 `required=true` 检查发生在导入 `main` 飞控入口之前。
